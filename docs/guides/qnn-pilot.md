# Проверка YOLO11s на CPU и Snapdragon HTP

Экспериментальный APK **Drone CV QNN Pilot** устанавливается как `ru.university.dronecv.qnn`. Сравнение запускается во вкладке **QNN**. Вкладки фото, камеры и журналов используют штатный CPU-путь.

## Первый прогон на Xiaomi 17 Pro

1. Перенесите `DroneCV-QNN-Pilot-r5.apk` и контрольные снимки в «Загрузки». Откройте APK через «Файлы» и установите. Для проверки используйте штатную HyperOS и обычную установку APK.
2. В приложении откройте **QNN → Выбрать кадры**. Выберите одни и те же сохранённые PNG/JPEG, включая кадры без дрона и с score около 0,50.
3. Выберите **Короткий → CPU и QNN HTP → Холодный запуск HTP**. Сохраните JSON. Проверьте `session_mode: cold`, время создания и `htp_confirmed: true` при `cpu_ep_fallback_disabled: true`. В общем прогоне один подготовленный тензор передаётся обеим сессиям.
4. Оставаясь во вкладке **QNN** и сохранив кадры, нажмите **Запустить**. Сохраните второй JSON. Сверьте `input_sha256` и `session_id` HTP между отчётами. Ожидаются `session_mode: reused`, `profile_from_earlier_run: true` и собственные p50/p95 повторного прогона. Проверьте решение при пороге 0,50 на каждом кадре.
5. Запишите версию HyperOS из настроек телефона. Если HTP откажет, сохраните JSON со стадией ошибки. При доступном ADB дополните его журналом процесса приложения с сообщениями QNN и FastRPC, пока приложение открыто. PID можно получить командой `adb shell pidof ru.university.dronecv.qnn` и передать в `adb logcat -d --pid PID`.

Для короткого прогона подходят три уже сохранённых PNG из папки проекта `YOLO11s — размер коптера/Фронтальный JPEG/inputs`. Кадр `w08_dx+1_dy-1.png` дал на CPU score 0,5058, `w08_dx+0_dy+0.png` дал 0,3526, а `w64_dx-2_dy+2.png` дал 0,5578. Это цифровые контрольные изображения. Для проверки на снимках со стенда добавьте реальные кадры с разных сторон порога.

## Сравнение скорости и нагрева на Xiaomi

1. Выберите 1–12 кадров для обоих прогонов. В режиме **Короткий** проверьте рамки и решение при `> 0,50`, а также p95 CPU. Для первого длительного сравнения подойдёт 2 кадр/с, если p95 CPU заметно ниже 500 мс. При высокой задержке выберите 1 кадр/с.
2. Отключите автояркость и выставьте одну яркость для обоих прогонов. Отсоедините зарядку и USB. Положите телефон в одном положении и оставьте приложение на экране. Перед началом дайте телефону остыть. Если есть термометр, отметьте одну точку корпуса и измеряйте её с того же расстояния в начале и конце каждого прогона.
3. Запустите **QNN → 15 минут → CPU** на выбранной частоте. Через 15 минут нажмите **Сохранить JSON**. Сверьте число пропусков и фактическую частоту. Если CPU теряет кадры, выберите меньшую частоту и повторите оба прогона на ней.
4. Дождитесь исходного теплового состояния при той же комнатной температуре. С термометром сверьте температуру в отмеченной точке. Выберите **QNN HTP** с теми же кадрами и частотой. Сохраните второй JSON и проверьте `htp_confirmed: true` и `cpu_ep_fallback_disabled: true`.
5. Сравните `ordered_inputs` по `input_sha256`, `target_fps`, `processed_frames`, `missed_slots` и p50/p95 по минутам. Для сравнения нагрева при равной нагрузке нужны одинаковый порядок входов, частота и сопоставимое число пропусков. Поле `thermal_samples` содержит уровни тепловых ограничений Android. Значение `0` означает отсутствие ограничений, `null` означает, что чтение недоступно. Температуру корпуса запишите отдельно. [Тепловой статус Android](https://developer.android.com/reference/android/os/PowerManager#getCurrentThermalStatus())

Длительное измерение начинается после создания, подготовки кадров и прогрева одной сессии. Кадры сортируются по хешам подготовленных тензоров и повторяются циклически. Пропущенный интервал остаётся в расписании, порядок следующих кадров сохраняется. В JSON сохранены времена создания и инициализации, фактическая частота и пропуски, p50/p95 по минутам и тепловой статус примерно каждые 5 секунд. Счётчики минут относятся к запланированным интервалам. Поле `overrun_ms` показывает задержку выхода из цикла за пределами окна измерения. **Отменить прогон** останавливает работу между вызовами ORT и позволяет сохранить частичный JSON с `outcome: cancelled`.

## Что смотреть в отчёте

- Холодный запуск здесь открывает новую сессию ORT в текущем процессе. `session_creation_ms` измеряет это открытие, включая компиляцию графа на HTP. При переиспользовании значение пустое. `initialization_ms` измеряет подготовку выбранного бэкенда, включая регистрацию плагина при холодном запуске или выбор уже открытой сессии. Проверка хеша модели выполняется до обоих замеров.
- На каждый кадр и бэкенд выполняются 4 прогревочных и 20 измеряемых инференсов. p50/p95 считаются по `runRaw()`, включая вызов ORT и перенос тензоров. Декодирование изображения, предобработка и NMS выполняются вне замера. Профиль HTP завершается после первого успешного прогревочного вызова.
- `htp_confirmed: true` требует успешный запуск с `backend_type=htp`, отключённый переход на CPU через `session.disable_cpu_ep_fallback=1` и события выполнения узлов с `QNNExecutionProvider` в профиле. На Xiaomi в `qnn_discovery` ожидаются `soc_model: SM8850` в параметрах провайдера, `expected_hexagon_version: 81` и `QNNExecutionProvider` с типом `NPU`. При отказе `setup_error` показывает стадию, а `qnn_discovery` сохраняет все устройства ORT до фильтрации и доступность нативных библиотек. Если есть только CPU-результаты, `comparison` остаётся пустым.
- Порог детекции строгий `score > 0.50`. Сравнение показывает отдельно совпадение решения о детекции и рамок. Для рамок требуется взаимно однозначное совпадение класса с IoU ≥ 0,90. JSON содержит координаты и score каждой рамки, IoU пар и максимальный score до порога/NMS, включая значения ниже 0,50. Значения в пределах 0,05 от порога помечаются. Отношение времени CPU к HTP добавляется при подтверждённом HTP.
- ONNX и входной тензор остаются FP32. QAIRT 2.52.0 может выполнять операции HTP с внутренней арифметикой FP16 на поддерживаемом SoC. [Документация QNN EP 2.8.0](https://github.com/onnxruntime/onnxruntime-qnn/blob/v2.8.0/docs/execution_providers/QNN-ExecutionProvider.md#configuration-options)
- Сессия HTP освобождается при выходе из вкладки, отмене или ошибке инференса HTP. Отмена срабатывает между вызовами ORT. Если нативный вызов уже идёт, интерфейс дождётся его возврата. Следующий запуск создаст новую сессию. CPU создаёт сессию для каждого прогона.

## Что подтверждено для SM8850/V81

- Xiaomi указывает Snapdragon 8 Elite Gen 5 и HyperOS для серии Xiaomi 17 Pro. Qualcomm указывает V81 для SM8850, а таблица QNN EP 2.8.0 сопоставляет SM8850 с V81. APK определяет SoC через Android и фильтрует устройства ORT до `QNNExecutionProvider/NPU`. [Xiaomi](https://ir.mi.com/static-files/e4830480-8ce9-45f8-a09d-64e40b2bdfac) · [Список Qualcomm](https://github.com/qualcomm/qidk/blob/master/Solutions/VisionSolution1-ObjectDetection-YoloNas/README.md#list-of-supported-devices) · [Таблица QNN EP 2.8.0](https://github.com/onnxruntime/onnxruntime-qnn/blob/v2.8.0/onnxruntime/core/providers/qnn/soc_utility/soc_table.h)
- В r4 ARM64 Stub и Hexagon Skel V81 побайтово совпадают с QNN Runtime 2.52.0. FastRPC получает каталог извлечённых библиотек через `ADSP_LIBRARY_PATH`, а приложение запрашивает `libcdsprpc.so` в манифесте. На штатной HyperOS предстоит проверить доступность библиотеки из приложения, открытие V81 Skel и успешный инференс. [Android-пример Qualcomm](https://github.com/onnxruntime/onnxruntime-qnn/tree/v2.8.0/java/src/test/android#qnn-builds) · [Правила Android для нативных библиотек](https://developer.android.com/guide/topics/manifest/uses-native-library-element)
- Для Android Qualcomm перечисляет QNN EP 2.8.0, Runtime 2.52.0 и проверенный ORT 1.29.0. ORT 1.31.1 с этими пакетами прошёл реальный прогон на Fold6 SM8650/V75. Цифры Fold6 относятся к этому устройству. [Матрица версий QNN EP](https://github.com/onnxruntime/onnxruntime-qnn/blob/v2.8.0/docs/execution_providers/QNN-ExecutionProvider.md#pre-built-packages)
- QNN EP документирует бинарный кэш для скомпилированного контекста, включая создание на ARM64 для описанного сценария с QDQ. В r4 используется открытая сессия в памяти. Ускорение первого запуска после перезапуска процесса за счёт дискового кэша для текущей FP32-модели пока не измерено. [QNN context binary cache](https://github.com/onnxruntime/onnxruntime-qnn/blob/v2.8.0/docs/execution_providers/QNN-ExecutionProvider.md#qnn-context-binary-cache-feature)

## Сборка

С установленной моделью из `ml/model_manifest.json` выполните из корня проекта:

```sh
./gradlew -PsnapdragonQnn=true :app:assembleQnn
python3 ml/scripts/verify_apk_model.py app/build/outputs/apk/qnn/app-qnn.apk
```

Вариант QNN использует ARM64, ONNX Runtime 1.31.1, QNN EP 2.8.0 и QNN Runtime 2.52.0. Нативные библиотеки извлекаются при установке, а их каталог передаётся FastRPC через `ADSP_LIBRARY_PATH`, как в примере Qualcomm. С этой комбинацией версий подтверждён инференс YOLO11s на Fold6 SM8650/V75. Проверка Xiaomi SM8850/V81 предстоит отдельно. [Официальный пример Android](https://github.com/onnxruntime/onnxruntime-qnn/tree/v2.8.0/java/src/test/android) · [Проверенные версии Android](https://github.com/onnxruntime/onnxruntime-qnn/blob/v2.8.0/docs/execution_providers/QNN-ExecutionProvider.md#pre-built-packages)

## Следующий этап

После подтверждения HTP подключить проверенный бэкенд к отдельному эксперименту **YOLO + LK**. Повторить один сценарий движения на Xiaomi для CPU + LK и QNN + LK с одинаковыми настройками ЛК и сцены. Сравнить частоту обновления координат, задержку от кадра до сигнала, число потерь и время повторного захвата. Результаты определят, нужна ли отдельная оптимизация ЛК.
