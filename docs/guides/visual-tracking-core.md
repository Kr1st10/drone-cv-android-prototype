# Визуальное сопровождение в камере

Для Android/CV-разработчика. CameraScreen подключает TrackingSession и OpenCvLkTracker к LiveController. YOLO ищет цель и периодически проверяет класс, LK обновляет положение между этими вызовами. В режиме «Фото» по-прежнему работает независимая детекция. [Владение кадрами](camera-frame-ingress.md).

## Реализованные компоненты

| Компонент | Назначение |
|---|---|
| GrayFrame / GrayHistory | Собственные неизменяемые upright grayscale-пиксели и ограниченная история |
| OpenCvLkTracker | Пирамидальный Lucas–Kanade по изображениям, forward/backward-проверка и сравнение внешнего вида |
| TrackingSession | Выбор первой цели, период YOLO, сопоставление на времени detector frame, потеря и инвалидирование |
| CorrectionPlan / ReplayedCorrection | Перенос рамки запоздавшего YOLO по реальным кадрам с отдельным экземпляром трекера |

OpenCV 4.12.0 закреплён в Version Catalog. Используется официальный Android AAR `org.opencv:opencv` (Apache-2.0), minSdk библиотеки 21; ABI приложения остаются arm64-v8a/x86_64. AAR добавляет нативные библиотеки; локальный универсальный debug APK для двух ABI занимает около 198 MiB. OpenCV загружается при первой попытке инициализации трека по кандидату YOLO.

## Что измеряет трекер

GoodFeaturesToTrack ищет до 32 углов внутри исходной рамки. Нужно минимум четыре точки и рамка не меньше 8×8 пикселей сетки LK. Если кандидат слишком мал или лишён текстуры, камера продолжает поиск и показывает число кандидатов YOLO отдельно от рамки сопровождения. LK использует окно 15×15, три уровня пирамиды; затем возвращает точки назад. Допускаются forward/backward error до 1 пикселя, согласованное смещение до 1,5 пикселя от медианы и сохранение минимум половины исходных точек. NCC с исходным фрагментом должен быть не ниже 0,6. Слабая текстура, выход рамки за изображение, разрыв кадров больше 150 мс или несогласованные точки дают потерю, без старых координат.

Это перенос рамки без изменения масштаба; масштаб позднее уточняет YOLO. Точки не добавляются с фона для продолжения слабого трека. Окно LK всё же захватывает окрестность точки: маленький дрон на текстурном фоне остаётся риском. Forward/backward и NCC уменьшают дрейф, но не доказывают принадлежность объекта к классу drone или физическую идентичность при пересечении целей.

TrackQuality хранит число точек, долю сохранившихся, медианную ошибку возврата и корреляцию. Отдельно TrackingObservation хранит последний YOLO confidence, метку его исходного кадра и ClassConfirmation. Ни correlation, ни retainedFraction не являются confidence классификации. TrackingObservation.confirmationAgeMs(nowElapsedNs) использует FrameStamp: при UNKNOWN или некорректном порядке часов возвращает null. Время доставки ответа YOLO не омолаживает подтверждение.

## Период и выбор цели

TrackingSession принимает кадры последовательно от одного владельца. Повторы, старые sequence/analyzer timestamps и несовпадающие generation/source игнорируются. По умолчанию запрос YOLO возможен через 500 мс по analyzerEntryNs. При потере, пропуске подтверждения, retainedFraction <0,7 или NCC <0,75 — через 100 мс. Запрос делается только по реально полученному кадру и когда предыдущий цикл камеры уже завершился; правила не предполагают фиксированный FPS. Жёсткий TTL подтверждения — 1000 мс от экспозиции исходного YOLO-кадра; при неизвестной базе используется timeout от analyzer entry, без заявления возраста экспозиции. Интервалы изображений дополнительно проверяются по capture timestamps, когда обе метки совместимы. Известный возраст кадра больше 250 мс отбрасывается. Параметры прототипа требуют измерений.

При первом поиске выбирается drone с максимальным confidence. Для существующей цели сравнение идёт с её рамкой **на исходном кадре запроса**: IoU ≥0,2, расстояние центров ≤0,6 диагонали рамки, отношение каждой стороны от 0,5 до 2. Если два кандидата проходят близко по IoU (разница <0,15), ответ неоднозначен и не корректирует цель. Более высокий confidence другой цели не даёт ей приоритет. Пропуск подтверждения оставляет хороший визуальный трек до TTL с classification=MISSED; потеря сбрасывает рамку и локальный trackId. Новое приобретение получает новый ID, не заявление о физической идентичности.

## Запоздавшая коррекция и владение

Порядок работы:

1. VisionWorker формирует GrayFrame после копирования/закрытия ImageProxy, вызывает observe и резервирует через requestYolo один снимок для YOLO. Снимки, не отобранные для YOLO, закрываются на VisionWorker после observe; отдельной очереди снимков нет.
2. DetectorWorker последовательно выполняет ORT фото и камеры, поэтому новый запрос может ждать уже поставленной работы. Перед infer проверяются ожидание и возраст; по окончании snapshot освобождается. Ответ передаётся владельцу TrackingSession, который вызывает prepareCorrection: выбирает цель на anchor frame и фиксирует неизменяемый набор истории.
3. CorrectionPlan.replay выполняется на ML-worker с отдельным VisualTracker, пока основной визуальный трек продолжает обновляться. Рамка последовательно переносится по изображениям; лимит времени по умолчанию 100 мс, проверяется между native calls. Один native call не прерывается.
4. Результат передаётся обратно владельцу. commit проверяет request identity, epoch, generation/source и TTL, затем догоняет не больше двух оставшихся кадров. В requestYolo и commit передаётся текущее elapsedRealtimeNanos: если вход остановился, старый кадр не становится свежим из-за отсутствия новых callback. Допустимый известный возраст последнего изображения/ожидания — до 250 мс. Если истории нет или отставание больше, коррекция закрывается и отбрасывается. Перед публикацией LiveController снова проверяет возраст кадра и TTL подтверждения: нативная работа могла пересечь дедлайн. Старую рамку нельзя просто приложить к новому кадру.

TrackingSession сам не создаёт executors и не вызывает ORT. Все методы TrackingSession вызываются последовательно на одном vision-владельце. CorrectionPlan.replay выполняется на ML-worker; ReplayedCorrection.close вызывается текущим владельцем коррекции. Перенос владения ReplayedCorrection между workers последовательный, без одновременных вызовов. finish вызывается при ошибке/отмене ORT или replay; заброшенный ReplayedCorrection обязан быть закрыт. После reset/close запоздалый commit закрывает ресурсы и не публикует координаты. LiveTracking хранит одну резервацию до завершения цепочки YOLO/replay/commit, в том числе при Stop и смене поколения. Нативная работа идёт вне блокировки LiveController; публикация сверяет generation/source под блокировкой. Сбросы на VisionWorker проверяют номер поколения.

GrayFrame не удерживает leased ARGB и не выдаёт свой массив наружу. Один кадр — максимум 1 MiB, история — максимум 32 кадра/8 MiB. Crop больше 1 MiB пикселей уменьшается для LK до площади около 640×480 с сохранением пропорций; размер полного upright crop остаётся в метаданных. Рамка и центр переводятся обратно, ошибки точек измеряются в сетке LK. Один выполняющийся запрос удерживает anchor, один replay plan может удерживать прежнюю историю, пока текущая заменяется. Это ограниченные дополнительные ссылки; native Mat/пирамиды LK, ARGB-пул 16 MiB и память процесса учитываются отдельно. Повторный replay одного plan отклоняется атомарным флагом. Один tracker нельзя передавать двум workers одновременно.

## Проверки и испытания

JVM-тесты проверяют геометрию grayscale, владение, границы истории, период запросов, выбор той же цели, неоднозначность, TTL, replay и устаревшие коррекции. Native LK проверяется отдельными Android-тестами на перемещаемом текстурном фрагменте, его исчезновении и непригодной текстуре. Синтетический фрагмент проверяет механику optical flow, не качество обнаружения дронов.

LiveTrackingIntegrationTest проверяет проход от копии кадра до публикации, задержанную коррекцию, Stop/rebind, TTL и раздельный экспорт. Для испытаний на Xiaomi 17 Pro запишите неподвижную и движущуюся камеру, одиночный дрон, пересечение двух целей и выход из кадра. Разметьте цель и её размеры, сравните частоту уникальных обновлений, p50/p95 от экспозиции, потери, ложное удержание фона, смены цели и время восстановления. По одному track_id нельзя установить физическую смену цели. 20–30 обновлений/с остаются ориентиром. Формат измерений — [сигнал и экспорт](latency-and-prediction.md).

Основания выбора API: [официальный LK-пример](https://github.com/opencv/opencv/blob/4.x/samples/python/lk_track.py), [Android-интеграция OpenCV](https://docs.opencv.org/4.12.0/d5/df8/tutorial_dev_with_OCV_on_Android.html). Реальные результаты проверок этого этапа фиксируются в PROJECT_STATE.
