# Ядро визуального трекинга

Для Android/CV-разработчика, продолжающего переход к редким вызовам YOLO. Это экспериментальное ядро в `tracking/`; оно пока **не подключено к CameraScreen/LiveController**. Приложение 0.5.2 продолжает независимо выбирать максимальный confidence в каждом обработанном YOLO-снимке. JSON сигнала v2 и его смысл не изменены. Подготовленный вход камеры описан в [владении кадрами](camera-frame-ingress.md).

## Реализованные компоненты

| Компонент | Назначение |
|---|---|
| GrayFrame / GrayHistory | Собственные неизменяемые upright grayscale-пиксели и ограниченная история |
| OpenCvLkTracker | Пирамидальный Lucas–Kanade по изображениям, forward/backward-проверка и сравнение внешнего вида |
| TrackingSession | Выбор первой цели, период YOLO, сопоставление на времени detector frame, потеря и инвалидирование |
| CorrectionPlan / ReplayedCorrection | Перенос рамки запоздавшего YOLO по реальным кадрам с отдельным экземпляром трекера |

OpenCV 4.12.0 закреплён в Version Catalog. Используется официальный Android AAR `org.opencv:opencv` (Apache-2.0), minSdk библиотеки 21; ABI приложения остаются arm64-v8a/x86_64. AAR добавляет нативные библиотеки; локальный универсальный debug APK для двух ABI занимает около 198 MiB. Инициализация OpenCV выполняется только при создании OpenCvLkTracker, не при открытии существующего экрана.

## Что измеряет трекер

GoodFeaturesToTrack ищет до 32 углов внутри исходной рамки. Нужно минимум четыре точки и рамка не меньше 8×8 пикселей. LK использует окно 15×15, три уровня пирамиды; затем возвращает точки назад. Допускаются forward/backward error до 1 пикселя, согласованное смещение до 1,5 пикселя от медианы и сохранение минимум половины исходных точек. NCC с исходным фрагментом должен быть не ниже 0,6. Слабая текстура, выход рамки за изображение, разрыв кадров больше 150 мс или несогласованные точки дают потерю, без старых координат.

Это перенос рамки без изменения масштаба; масштаб позднее уточняет YOLO. Точки не добавляются с фона для продолжения слабого трека. Окно LK всё же захватывает окрестность точки: маленький дрон на текстурном фоне остаётся риском. Forward/backward и NCC уменьшают дрейф, но не доказывают принадлежность объекта к классу drone или физическую идентичность при пересечении целей.

TrackQuality хранит число точек, долю сохранившихся, медианную ошибку возврата и корреляцию. Отдельно TrackingObservation хранит последний YOLO confidence, метку его исходного кадра и ClassConfirmation. Ни correlation, ни retainedFraction не являются confidence классификации. TrackingObservation.confirmationAgeMs(nowElapsedNs) использует FrameStamp: при UNKNOWN или некорректном порядке часов возвращает null. Время доставки ответа YOLO не омолаживает подтверждение.

## Период и выбор цели

TrackingSession принимает кадры последовательно от одного владельца. Повторы, старые sequence/analyzer timestamps и несовпадающие generation/source игнорируются. По умолчанию запрос YOLO возможен через 500 мс по analyzerEntryNs. При потере, пропуске подтверждения, retainedFraction <0,7 или NCC <0,75 — через 100 мс. Запрос делается только по реально полученному кадру и при свободном ML-worker; правила не предполагают фиксированный FPS. Жёсткий TTL подтверждения — 1000 мс от экспозиции исходного YOLO-кадра; при неизвестной базе используется timeout от analyzer entry, без заявления возраста экспозиции. Интервалы изображений дополнительно проверяются по capture timestamps, когда обе метки совместимы. Известный возраст кадра больше 250 мс отбрасывается. Параметры прототипа требуют измерений.

При первом поиске выбирается drone с максимальным confidence. Для существующей цели сравнение идёт с её рамкой **на исходном кадре запроса**: IoU ≥0,2, расстояние центров ≤0,6 диагонали рамки, отношение каждой стороны от 0,5 до 2. Если два кандидата проходят близко по IoU (разница <0,15), ответ неоднозначен и не корректирует цель. Более высокий confidence другой цели не даёт ей приоритет. Пропуск подтверждения оставляет хороший визуальный трек до TTL с classification=MISSED; потеря сбрасывает рамку и локальный trackId. Новое приобретение получает новый ID, не заявление о физической идентичности.

## Запоздавшая коррекция и владение

Предусмотренный порядок при последующем подключении:

1. VisionWorker формирует GrayFrame после копирования/закрытия ImageProxy, вызывает observe и резервирует запрос через requestYolo при свободном DetectorWorker.
2. DetectorWorker единолично выполняет ORT. Ответ передаётся владельцу TrackingSession, который вызывает prepareCorrection: выбирает цель на anchor frame и фиксирует неизменяемый набор истории.
3. CorrectionPlan.replay выполняется на ML-worker с отдельным VisualTracker, пока основной визуальный трек продолжает обновляться. Рамка последовательно переносится по изображениям; лимит времени по умолчанию 100 мс, проверяется между native calls. Один native call не прерывается.
4. Результат передаётся обратно владельцу. commit проверяет request identity, epoch, generation/source и TTL, затем догоняет не больше двух оставшихся кадров. В requestYolo и commit передаётся текущее elapsedRealtimeNanos: если вход остановился, старый кадр не становится свежим из-за отсутствия новых callback. Допустимый известный возраст последнего изображения/ожидания — до 250 мс. Если истории нет или отставание больше, коррекция закрывается и отбрасывается. Старую рамку нельзя просто приложить к новому кадру.

TrackingSession сам не создаёт executors и не вызывает ORT. Все методы TrackingSession вызываются последовательно на одном vision-владельце. CorrectionPlan.replay выполняется на ML-worker; ReplayedCorrection.close вызывается текущим владельцем коррекции. Перенос владения ReplayedCorrection между workers последовательный, без одновременных вызовов. finish вызывается при ошибке/отмене ORT или replay; заброшенный ReplayedCorrection обязан быть закрыт. После reset/close запоздалый commit закрывает ресурсы и не публикует координаты. При интеграции требуются также generation guards для самих queued reset/callback и общий ORT busy gate, включая фото.

GrayFrame не удерживает leased ARGB и не выдаёт свой массив наружу. Один кадр — максимум 1 MiB, история — максимум 32 кадра/8 MiB. Один выполняющийся запрос удерживает anchor, один replay plan может удерживать прежнюю историю, пока текущая заменяется. Это ограниченные дополнительные ссылки; native Mat/пирамиды LK, ARGB-пул 16 MiB и память процесса учитываются отдельно. Повторный replay одного plan отклоняется атомарным флагом. Один tracker нельзя передавать двум workers одновременно.

## Проверки и следующий шаг

JVM-тесты проверяют геометрию grayscale, владение, границы истории, период запросов, выбор той же цели, неоднозначность, TTL, replay и устаревшие коррекции. Native LK проверяется отдельными Android-тестами на перемещаемом текстурном фрагменте, его исчезновении и непригодной текстуре. Синтетический фрагмент проверяет механику optical flow, не качество обнаружения дронов.

Следующий этап — подключить ядро к [существующему входу](camera-frame-ingress.md), добавить раздельные tracking/YOLO показатели и UI/JSON с явными версиями. Текущий экспорт пока не содержит TrackingObservation. После интеграции на движущейся цели измеряются уникальные обновления/с, экспозиция → публикация p50/p95, потери, ложное удержание фона, смены цели и восстановление. Ориентир 20–30 обновлений/с не подтверждён тестами ядра. Нужны реальные видеозаписи с маленькими дронами, движением камеры, разметкой идентичности и размеров целей.

Основания выбора API: [официальный LK-пример](https://github.com/opencv/opencv/blob/4.x/samples/python/lk_track.py), [Android-интеграция OpenCV](https://docs.opencv.org/4.12.0/d5/df8/tutorial_dev_with_OCV_on_Android.html). Реальные результаты проверок этого этапа фиксируются в PROJECT_STATE.
