# Типовые изменения и проверки

Инструкции для разработчика текущей одномодульной архитектуры. Они описывают будущие изменения; в документационном задании эти правки кода, экспорт модели и измерения не выполнялись.

## Изменить порог или параметры postprocessing

1. Определите нужный контур: камера получает порог из `DroneApp`/UI; фото и Python-эталон используют собственный default. Сверьте [конфигурацию](../reference/configuration.md#настройки-во-время-работы).
2. Сохраните строгое сравнение score и NMS, нормализованные координаты и invalidation старых результатов при смене порога. Не меняйте модель одновременно с настройкой порога, если нужен интерпретируемый эксперимент.
3. Проверьте PostprocessorTest и controller tests, затем сборку по [testing](../development/testing.md). На реальных разрешённых данных отдельно оцените ложные срабатывания/пропуски; изменение порога не обещает устранения ошибок.
4. Обновите описание defaults и протокол измерения в том же PR. Не переносите метрики исследовательской выборки в заявление о полевом качестве.

## Заменить Android-модель

1. Установите происхождение/права, совместимость тензоров и способ воспроизведения. Канонические артефакты — [MODEL](../../ml/MODEL.md) и [manifest](../../ml/model_manifest.json).
2. Проверьте raw-output и конечный результат на контрольных входах; отдельно оцените независимые малые цели и негативы по существующим исследовательским протоколам. Не открывайте sealed test для подбора параметров.
3. Согласованно обновите source/export/android поля манифеста, документацию модели и необходимые проверки формата. Установщик, Gradle BuildConfig/verifyDroneModel и runtime получают Android-путь/SHA из манифеста; не создавайте второе ручное значение в Kotlin.
4. Установите проверенный файл, выполните сборку/JVM/AndroidTest compilation/lint и verify_apk_model. На устройстве проверьте реальные inference/geometry/lifecycle и ресурсы; CPU Python не заменяет эти испытания.
5. Не коммитьте веса/датасеты и не отключайте SHA-проверку. Опишите миграцию контракта, если меняются тензоры/классы/экспорт; старый serializer диагностики имеет фиксированные сведения о YOLO11s 640 и тоже потребует проверки.

Это процедура изменения, а не разрешение самостоятельно выбирать новую архитектуру, лицензию или распространять веса.

## Добавить поле диагностики

1. Зафиксируйте смысл, единицу, источник и временную базу. Для недоступного значения используйте null; неизвестные CameraX drops нельзя выводить из разницы callbacks/completions.
2. Обновите типы/serializer в [diagnostics](../../app/src/main/java/ru/university/dronecv/diagnostics), соответствующий consumer [analyze_android_sessions.py](../../ml/scripts/analyze_android_sessions.py) и [описание данных](../reference/data-model.md).
3. Сохраните совместимость старых JSON либо явно опишите несовместимый формат. Изменение version number само по себе не обеспечивает миграцию потребителей.
4. Проверьте пустой/прерванный отчёт, null, escaping, поздний callback предыдущего token и capacity; выполните JVM/JSON device tests, Python analyzer tests в подготовленном окружении. Проверьте экспорт/разбор настоящего файла на устройстве.
5. Подсчёт/экспорт оставьте в фоне. Оцените накладные расходы измерений отдельно от скорости без диагностики.

## Изменить preview, ориентацию или камеру

1. Начните с [CameraPreview](../../app/src/main/java/ru/university/dronecv/camera/CameraPreview.kt), а mapping сверяйте с [потоками данных](../architecture/data-flow.md).
2. Сохраните общий ViewPort и UseCaseGroup, инвалидируйте результат до rebind, назначайте новый source при активации, закрывайте все ImageProxy в finally. Не добавляйте очередь за analyzer и повторный поворот рамок.
3. Проверьте обе альбомные ориентации, resize, фон, Stop/restart, новый zoom/ID и позднюю ошибку старого binding. Панель не должна менять размер preview при появлении результата.
4. Выполните локальную Android-проверку, device integration и [CAMERA_QA](../CAMERA_QA.md). Отдельно фиксируйте неподдерживаемую комбинацию потоков и возможность OEM скрыть метаданные.

## Проверить стенд без обучения

Используйте [README галереи](../../lab/monitor_test/README.md) для загрузки/валидации изображений и фиксированной выборки, [протокол](../../lab/monitor_test/PROTOCOL.md) — для наблюдений. Запишите phone/zoom/distance и фактический порог Android: в quick порог ведётся отдельно, для сохранения в записи нужен advanced. Для сравнения повторяйте ту же sample и порядок. Сохраните CSV/JSON до очистки localStorage. Не передавайте тестовый набор в обучение или подбор порогов и не переводите размер изображения на мониторе в реальную дальность.

После любого сценария проверьте [CONTRIBUTING](../../CONTRIBUTING.md): документация, результаты проверок и ограничения обновляются вместе с изменением.
