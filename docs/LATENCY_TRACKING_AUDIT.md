## Что означают нынешние метрики

`pipeline_ms` начинается непосредственно перед `backend.infer` и заканчивается после его возврата. Это включает конвертацию, подготовку тензора, ORT, NMS и сопутствующие действия backend; на первом кадре сюда может попасть создание сессии модели. Захват, экспозиция, ISP и ожидание до analyzer остаются за границей замера. Время публикации результата, отрисовки и отправки внешнего сигнала также не входит.

Это видно в [LiveController:129](https://github.com/Kr1st10/drone-cv-android-prototype/blob/acb3e9ea62626ea3226c281a273fc083f2c5b67c/app/src/main/java/ru/university/dronecv/camera/LiveController.kt#L129). Экспорт прямо оставляет `frame_to_display_latency_ms` и `camera_frames_dropped` равными `null`: [DiagnosticReport:37](https://github.com/Kr1st10/drone-cv-android-prototype/blob/acb3e9ea62626ea3226c281a273fc083f2c5b67c/app/src/main/java/ru/university/dronecv/diagnostics/DiagnosticReport.kt#L37). Поля для времени экспозиции, ID кадра и отправки цели отсутствуют. `frames[].offset_ms` означает положение завершённой обработки относительно начала диагностической сессии; `resources[].offset_ms` отмечает время пробы ресурсов.

Надпись «Полный цикл» в UI относится к backend pipeline. Для новой задачи её следует уточнить, чтобы это число не принимали за время от экспозиции до действия. FPS показывает темп завершения обработки и не определяет возраст координат.

Сброс рамок через 1,5 с отсчитывается после публикации результата. Без `t_capture` это не ограничивает возраст исходного наблюдения: только что показанная рамка уже относится к более раннему кадру. KEEP_ONLY_LATEST уменьшает накопление кадров перед обработкой, но не устраняет время работы камеры и самой модели.

В диагностическом JSON есть версия приложения, SHA модели, тип сборки, число потоков и прогрев, но нет SHA сборки кода и параметров конкретного захвата. В исследуемой `main` версия приложения всё ещё 0.4.0 / code 4. Для последующих сравнений нужно добавить идентификатор сборки, фактические камеру/зум/размер crop и условия записи.

## Детекция, сопровождение и прогноз

Детекция отвечает на вопрос, где в отдельном кадре находится объект заданного класса. Сейчас модель возвращает `drone`, confidence и рамку. У модели один класс; она не различает типы дронов и может ошибочно относить к этому классу птиц и самолёты. Рабочие Android-веса по-прежнему прежние: наличие исследовательских дообучений в репозитории не означает замены модели в APK.

Сопровождение связывает наблюдения одного объекта во времени, сохраняет его ID и оценивает движение. Оно может работать с объектом, класс которого неизвестен. В текущем коде `generation`, `source` и `revision` защищают от устаревших callback и результатов UI; это не идентификаторы дрона. Повторяющиеся YOLO-рамки также не образуют трек автоматически.

[dut63_tracking.py](https://github.com/Kr1st10/drone-cv-android-prototype/blob/acb3e9ea62626ea3226c281a273fc083f2c5b67c/ml/scripts/dut63_tracking.py#L1) выбирает отдельные размеченные кадры из видео DUT для аудита данных. Он не сопровождает объект в приложении и не предсказывает его движение.

Прогноз оценивает положение на будущий момент. Для первой версии имеет смысл проверять короткий прогноз в координатах изображения, чтобы компенсировать измеренный возраст наблюдения. По одной камере без дополнительных условий нельзя обещать восстановление трёхмерной траектории полёта. Поворот телефона или стабилизатора тоже смещает объект в изображении; это необходимо учитывать при оценке движения.

## Как определить требуемую задержку

Для первой метрики предлагается конечная точка выдачи координат выбранного объекта в интерфейс действия. Отправка пакета, его получение контроллером и начало движения механики должны иметь собственные границы измерения.

```text
t_exposure → t_analyzer → t_conversion → t_preprocess → t_ort → t_postprocess → t_emit

L_exposure_to_emit = t_emit - t_exposure
```

Текущий `pipeline_ms` покрывает лишь участок обработки внутри backend. Для всей цепочки нужны ID кадра, исходный timestamp, отметки начала/конца стадий, время готовности цели и время фактической передачи результата. Отдельно считать холодный запуск, установившийся режим, p50/p95/p99 и возраст последней доступной цели при каждом сигнале. Для p99 потребуется достаточная выборка; прогнозные точки нужно отличать от новых измерений.

Android определяет `CaptureResult.SENSOR_TIMESTAMP` как начало экспозиции первой строки активной области сенсора. Это возможная опора для требуемого начала замера; timestamp необходимо связать с тем же кадром ImageAnalysis. При rolling shutter время наблюдения конкретной строки отличается, поэтому позднее пригодятся `SENSOR_EXPOSURE_TIME` и `SENSOR_ROLLING_SHUTTER_SKEW`. [Документация CaptureResult](https://developer.android.com/reference/android/hardware/camera2/CaptureResult#SENSOR_TIMESTAMP), обращение 04.11.2026.

Сначала проверить `SENSOR_INFO_TIMESTAMP_SOURCE`. При REALTIME sensor timestamp сопоставим с `SystemClock.elapsedRealtimeNanos()`; при UNKNOWN прямое сравнение с часами приложения не гарантируется. В таком случае следует сохранять ограничения и не выдавать разность несогласованных часов за измерение. [Документация CaptureResult](https://developer.android.com/reference/android/hardware/camera2/CaptureResult#SENSOR_TIMESTAMP).

Текущий `System.nanoTime()` пригоден для внутренних интервалов, но его нельзя без проверки смешивать с sensor timestamp. `elapsedRealtimeNanos()` включает глубокий сон, а база `nanoTime()` на Android связана с uptime. [Документация SystemClock](https://developer.android.com/reference/android/os/SystemClock), обращение 04.11.2026. У `ImageInfo.timestamp` значение зависит от источника изображения: для выбранного потока CameraX нужно подтвердить соответствие Camera2-метаданным. [Документация ImageInfo](https://developer.android.com/reference/androidx/camera/core/ImageInfo#getTimestamp()), обращение 04.11.2026.

В приложении уже есть Camera2 capture callback для physical ID: [CameraPreview:164](https://github.com/Kr1st10/drone-cv-android-prototype/blob/acb3e9ea62626ea3226c281a273fc083f2c5b67c/app/src/main/java/ru/university/dronecv/camera/CameraPreview.kt#L164). Это место можно рассмотреть для сбора метаданных; сейчас sensor timestamp и экспозиция там не читаются. Время прихода callback само по себе не является началом экспозиции.

## В каком пикселе находится объект

Для текущего результата доступны рамка `left/top/right/bottom` в диапазоне 0…1 и размеры `W/H` повёрнутого crop. Непрерывные координаты центра можно получить без нового инференса:

```text
cx = (left + right) × W / 2
cy = (top + bottom) × H / 2
```

Это центр рамки в видимой области обработанного изображения. Он не равен автоматически координатам полного сенсора или пикселям экрана; [CameraGeometry](https://github.com/Kr1st10/drone-cv-android-prototype/blob/acb3e9ea62626ea3226c281a273fc083f2c5b67c/app/src/main/java/ru/university/dronecv/camera/CameraGeometry.kt#L8) отдельно масштабирует рамку в превью. Для целочисленного пикселя нужно определить округление и ограничить индекс диапазонами 0…W−1 и 0…H−1.

Дальнейшему интерфейсу цели потребуются выбранный объект, frame ID, timestamp наблюдения, система координат, размеры изображения, confidence и признак «измерение/прогноз». При нескольких обнаружениях нужен выбор цели и сохранение её ID. Сейчас отдельного сообщения с этим набором полей и отправителя такого сообщения нет.

## Очередность следующих работ

1. Добавить измерение «экспозиция → выдача цели» и сохранить его рядом с существующими стадиями. Подтвердить временную базу камеры, проверить соответствие кадров и метаданных, определить конец выдачи сигнала. Измерить целевой телефон в повторяемых условиях. Сохранить старые метрики под точными названиями.
2. Использовать готовый режим и протокол сравнения 1/2/4 потоков, затем отдельно проверять другие способы исполнения или более лёгкую модель. Оценивать задержку вместе с качеством на маленьких дронах, ложными срабатываниями, температурой и памятью. Ускорение заранее не установлено; смена provider или модели требует своей проверки.
3. Добавить ID цели и сопровождение с периодической проверкой детектором. Для быстрых обновлений между долгими YOLO-вызовами потребуется отдельный короткий путь обработки кадров: трекер на том же заблокированном `DetectorWorker` не сможет обновляться во время инференса. При передаче кадра между потоками нужно пересмотреть владение буферами, сохранив ограничение очередей.
4. После появления достоверных timestamps и истории цели проверять короткий прогноз положения к моменту выдачи сигнала. Например, модель постоянной скорости или фильтр Калмана могут быть исходной гипотезой; проверять их нужно на видеопоследовательностях с разметкой по времени. Измерять ошибку прогноза, потери цели и смены ID. Старый прогноз не должен маскироваться под свежий кадр.
