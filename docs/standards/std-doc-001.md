# STD-DOC-001. Стандарт технической документации программного проекта

**Версия:** 1.0  
**Статус:** шаблон внутреннего стандарта для утверждения командой  
**Владелец:** технический руководитель / назначенный ответственный за документацию  
**Область применения:** исходный код, сервисы, библиотеки, приложения и их эксплуатационная документация  
**Формат по умолчанию:** Markdown в репозитории с исходным кодом

> Это **внутренний стандарт-шаблон**, а не официальный ГОСТ или ISO. Для регулируемых проектов, договорной документации и ЕСПД необходимо дополнительно применить обязательные требования заказчика и соответствующих стандартов.

## 1. Цель и область действия

1.1. Документация должна позволять новому участнику команды понять назначение проекта, запустить его, изменить и проверить код, разобраться в интерфейсах и безопасно эксплуатировать систему — без поиска критически важной информации в личной переписке.

1.2. Стандарт обязателен для новых проектов и для изменений, затрагивающих публичное поведение, настройку, архитектуру, развёртывание, безопасность или эксплуатацию существующего проекта.

1.3. Используются три уровня требований:

- **ОБЯЗАТЕЛЬНО** — условие приёмки; отклонение требует явно согласованного исключения.
- **РЕКОМЕНДУЕТСЯ** — стандартная практика; допускается обоснованная альтернатива.
- **ДОПУСКАЕТСЯ** — необязательная практика.

1.4. Аудитории: пользователи продукта, разработчики, интеграторы API, тестировщики, специалисты эксплуатации и информационной безопасности. Каждая страница должна иметь понятную целевую аудиторию и цель.

## 2. Принципы

- **Единый источник истины.** Для каждого факта (например, параметра конфигурации) назначается каноническое место; остальные документы ссылаются на него.
- **Документация как код.** Текст хранится в системе контроля версий, проходит review и проверку в CI.
- **Ориентация на задачи.** Инструкции описывают достижимый результат, необходимые условия, шаги и проверку успеха.
- **Точность.** Описывается фактическое, а не предполагаемое поведение версии системы.
- **Воспроизводимость.** Команды, примеры запросов и конфигурации проверяются в заявленной среде.
- **Безопасность.** Секреты, реальные персональные данные и закрытые ключи не публикуются.
- **Доступность.** Понятная структура, подписи рисунков, альтернативное описание нетекстовых элементов.

## 3. Обязательный набор документов

| Документ | Когда обязателен | Минимальное содержание |
|---|---|---|
| `README.md` | Для каждого репозитория | Назначение, требования, быстрый старт, ссылки, лицензирование/контакт при применимости |
| `docs/index.md` | Для проектов с несколькими разделами документации | Навигация, аудитории, краткая карта разделов |
| `docs/getting-started.md` | Для проектов, требующих настройки или нескольких шагов запуска | Предусловия, установка, запуск, проверка, устранение типовых ошибок |
| `docs/architecture/overview.md` | Для сервисов, приложений и многокомпонентных систем | Контекст, компоненты, границы, потоки данных, зависимости |
| `docs/reference/api.md` или спецификация OpenAPI | Если есть API для других компонентов или пользователей | Контракты, авторизация, ошибки, примеры, версия |
| `docs/reference/configuration.md` | Если приложение настраивается | Параметры, типы, значения по умолчанию, примеры, влияние изменения |
| `docs/deployment.md` | Для развёртываемых приложений и сервисов | Среды, зависимости, порядок выпуска, откат, проверка |
| `docs/operations/runbook.md` | Для сервисов, сопровождаемых в эксплуатации | Мониторинг, диагностика, типовые инциденты, восстановление, эскалация |
| `docs/development/testing.md` | При совместной разработке | Команды тестов, требования к качеству, локальная среда |
| `CONTRIBUTING.md` | При нескольких контрибьюторах или открытой разработке | Ветки, оформление PR, тестирование, review |
| `CHANGELOG.md` | Для версионируемых релизов | Изменения, несовместимости, исправления, миграции |
| `SECURITY.md` | Для публичных или чувствительных проектов | Как сообщать об уязвимостях, безопасный канал, границы раскрытия |
| `docs/architecture/decisions/` | При существенных архитектурных решениях | Записи ADR с контекстом, решением и последствиями |

Если документ неприменим, допустимо не создавать его, но причина должна быть очевидна из типа проекта или зафиксирована в `docs/index.md`. Критически важная информация не должна существовать только в задачах трекера или чате.

## 4. Требования к содержанию

### 4.1. `README.md`

ОБЯЗАТЕЛЬНО указывать:
1. Название и назначение проекта (1–3 предложения).
2. Основные возможности и границы ответственности.
3. Минимальные требования (язык, runtime, инфраструктура).
4. Команды установки и запуска.
5. Проверку успешного запуска.
6. Ссылки на подробную документацию и поддержку.

РЕКОМЕНДУЕТСЯ указывать статус проекта, поддерживаемые версии, лицензию, ограничения и информацию о вкладе.

### 4.2. Руководство быстрого старта

ОБЯЗАТЕЛЬНО указывать исходные условия, точные команды, ожидаемый результат, способ остановки/очистки и решение наиболее вероятных ошибок. Команды должны выполняться в обозначенном окружении без догадок пользователя.

### 4.3. Архитектура

ОБЯЗАТЕЛЬНО описывать назначение системы, внешние системы, границы доверия, ключевые компоненты, взаимодействия и хранилища данных. Для сложных систем РЕКОМЕНДУЕТСЯ применять модель C4: контекст, контейнеры и при необходимости компоненты. Схема не заменяет текст; для неё нужен короткий разбор.

### 4.4. API и интеграции

Для каждого публичного метода ОБЯЗАТЕЛЬНО документировать: метод и путь/имя операции, назначение, аутентификацию и авторизацию, входные параметры и их типы, обязательность, ограничения, структуру ответа, коды ошибок, пагинацию/лимиты при наличии, совместимость, примеры запросов и ответов. REST API РЕКОМЕНДУЕТСЯ описывать посредством OpenAPI, генерируя справочник из проверяемого контракта.

### 4.5. Конфигурация

Каждый параметр ОБЯЗАТЕЛЬНО описывать по схеме: **имя → назначение → тип → обязательность → значение по умолчанию → допустимые значения → пример → влияние изменения**. Секретные значения показываются только заглушками и указываются через механизм управления секретами.

### 4.6. Развёртывание и эксплуатация

ОБЯЗАТЕЛЬНО описывать предпосылки, порядок развёртывания, миграции, health checks, резервное копирование и восстановление (если есть состояние), откат, логи, метрики и типовые сбои. Любая опасная команда должна быть помечена предупреждением, окружением и последствиями.

### 4.7. Разработка и тестирование

ОБЯЗАТЕЛЬНО указывать команды установки зависимостей, запуска линтера, тестов, сборки и локальной проверки. Следует описать обязательные проверки pull request, соглашения по веткам и изменениям схемы/контрактов.

### 4.8. Изменения и миграции

В `CHANGELOG.md` РЕКОМЕНДУЕТСЯ группировать изменения как **Added / Changed / Deprecated / Removed / Fixed / Security**. Несовместимые изменения ОБЯЗАТЕЛЬНО выделять и сопровождать инструкцией миграции. Правила версионирования продукта указываются отдельно (например, SemVer, если проект его использует).

## 5. Единый шаблон страницы

У каждой содержательной страницы ОБЯЗАТЕЛЬНО должны быть:
- **Заголовок:** однозначное название действия, понятия или интерфейса.
- **Назначение:** что читатель узнает или выполнит.
- **Область применимости:** версия, компонент, окружение.
- **Основной материал:** шаги, описание, спецификация или объяснение.
- **Проверка результата:** где применимо — ожидаемое поведение и критерий успеха.
- **Ограничения и ошибки:** существенные условия и неисправности.
- **Связанные документы:** ссылки на канонические источники.

Для ключевых страниц РЕКОМЕНДУЕТСЯ хранить владельца и дату проверки в метаданных. Например:

```yaml
---
title: "Развёртывание сервиса"
owner: "platform-team"
status: "approved"
last_reviewed: "2026-10-01"
applies_to: "v2.x"
---
```

Поля являются примером внутреннего соглашения, а не универсальным стандартом YAML-метаданных.

## 6. Правила оформления и языка

### 6.1. Структура и навигация

- ОБЯЗАТЕЛЬНО: один заголовок `#` (H1) на страницу; далее уровни `##`, `###` по иерархии, без пропусков.
- ОБЯЗАТЕЛЬНО: говорящие названия файлов в `lowercase-kebab-case.md`; кодировка UTF-8 и окончания строк LF.
- ОБЯЗАТЕЛЬНО: относительные ссылки для файлов одного репозитория; проверка неработающих ссылок.
- РЕКОМЕНДУЕТСЯ: разделять материалы на четыре вида — tutorial, how-to, reference, explanation — по подходу Diátaxis; не смешивать их без причины.
- РЕКОМЕНДУЕТСЯ: краткое оглавление для длинных страниц (например, от 5–7 разделов).

### 6.2. Стиль

- Писать простым, точным языком, избегать канцеляризмов и неопределённых слов («обычно быстро», «при необходимости легко»).
- В инструкциях использовать повелительное наклонение: «Откройте», «Запустите», «Проверьте».
- Аббревиатуры расшифровывать при первом употреблении; один термин — одно значение.
- Отличать факт, предположение, рекомендацию и известное ограничение.
- Даты записывать в ISO 8601 (`2026-11-04`), время — с часовым поясом, размеры — с единицами.
- Ссылки оформлять смысловым текстом, не «нажмите здесь».
- Длинные абзацы разбивать по смыслу; таблицы применять для сравнения однотипных сущностей.

### 6.3. Код, команды и примеры

- ОБЯЗАТЕЛЬНО ставить язык у блока кода (`bash`, `python`, `json`, `yaml` и т. п.).
- Указывать рабочий каталог и среду выполнения, если это неочевидно.
- Помечать заменяемые значения явно: `<YOUR_TOKEN>`, `example.com`, `task-123`; пояснять их назначение.
- Примеры должны быть синтаксически корректными, применимыми к заявленной версии и, по возможности, проверяться автоматически.
- Не помещать реальный пароль, токен, ключ, персональные или производственные данные.
- Для потенциально разрушительных команд приводить предупреждение и способ безопасной проверки.

### 6.4. Схемы и изображения

- Подписывать схемы; объяснять ключевые обозначения и направления потоков.
- РЕКОМЕНДУЕТСЯ хранить диаграммы в текстовом формате (Mermaid, PlantUML) рядом с документацией.
- Для изображений ОБЯЗАТЕЛЬНО давать альтернативное описание, если изображение несёт смысл.

## 7. Документирование исходного кода

7.1. Публичные модули, классы, функции и интерфейсы ОБЯЗАТЕЛЬНО сопровождать описанием назначения, параметров/типов, результата, исключений и нетривиальных побочных эффектов. Использовать принятый для языка формат: Python docstrings, Javadoc, JSDoc/TSDoc, XML documentation и др.

7.2. Комментарии в теле функции должны объяснять **почему** принято решение и какие действуют инварианты, а не дублировать **что** очевидно из кода.

7.3. РЕКОМЕНДУЕТСЯ документировать границы применимости алгоритмов, допущения, особенности потокобезопасности, производительности и совместимости.

**Пример (Python):**

```python
def calculate_total(amount: float, tax_rate: float) -> float:
    """Вычисляет итоговую сумму с налогом.

    Args:
        amount: Неотрицательная сумма до налога.
        tax_rate: Ставка в долях единицы, например 0.2.

    Returns:
        Итоговая сумма с налогом.

    Raises:
        ValueError: Если сумма или ставка отрицательна.
    """
    if amount < 0 or tax_rate < 0:
        raise ValueError("Сумма и ставка должны быть неотрицательными")
    return amount * (1 + tax_rate)
```

## 8. Примеры проектной документации

### 8.1. Фрагмент `README.md`

Ниже **вымышленный** проект TaskFlow. Команды иллюстрируют оформление и требуют адаптации к реальному репозиторию.

````markdown
# TaskFlow

TaskFlow — сервис хранения и отслеживания задач по HTTP API.

## Требования

- Docker Engine с поддержкой Compose.
- Порты 8080 и 5432 свободны на локальной машине.

## Быстрый старт

1. Создайте локальную конфигурацию:

   ```bash
   cp .env.example .env
   ```

2. Запустите сервисы:

   ```bash
   docker compose up -d
   ```

3. Проверьте готовность:

   ```bash
   curl --fail http://localhost:8080/health
   ```

   Ожидаемый результат: HTTP 200.

## Документация

- [Начало работы](docs/getting-started.md)
- [Архитектура](docs/architecture/overview.md)
- [API](docs/reference/api.md)
- [Развёртывание](docs/deployment.md)
````

### 8.2. Карточка API

**Операция:** `GET /v1/tasks/{task_id}`  
**Назначение:** получить задачу по идентификатору.  
**Авторизация:** Bearer token, право `tasks:read`.  
**Параметр:** `task_id` — обязательная строка, идентификатор задачи.  
**Успех:** `200 OK`, JSON-объект задачи.  
**Ошибки:** `401 Unauthorized`, `403 Forbidden`, `404 Not Found`.

```bash
curl --request GET \
  --header "Authorization: Bearer <YOUR_TOKEN>" \
  "https://api.example.com/v1/tasks/task-123"
```

```json
{
  "id": "task-123",
  "title": "Проверить документацию",
  "status": "open"
}
```

В реальном проекте также ОБЯЗАТЕЛЬНО описать модель данных, ограничения, версионирование и фактические ответы об ошибках. Этот пример не является спецификацией работающего API.

### 8.3. Решение по архитектуре (ADR)

```markdown
# ADR-0001: Использовать PostgreSQL для хранения задач

Статус: принят
Дата: 2026-10-01

## Контекст
Нужны транзакции и выборки по нескольким полям задач.

## Решение
Использовать PostgreSQL как основное хранилище.

## Альтернативы
SQLite — проще локально, но ограничивает целевой сценарий
многопользовательского развёртывания.

## Последствия
Появляется отдельный сервис БД; необходимы миграции,
резервное копирование и мониторинг.
```

### 8.4. Фрагмент runbook

```markdown
# Runbook: недоступен endpoint /health

## Признак
Проверка /health возвращает не-2xx в течение 5 минут.

## Диагностика
1. Проверьте статус контейнеров: `docker compose ps`.
2. Посмотрите логи: `docker compose logs --tail=200 app`.
3. Проверьте доступность базы данных и последние миграции.

## Восстановление
Следуйте утверждённой процедуре отката из docs/deployment.md.
Не удаляйте тома данных при диагностике.

## Проверка
Убедитесь, что /health возвращает HTTP 200, а ошибок в логах нет.

## Эскалация
Обратитесь к дежурной группе согласно внутреннему расписанию.
```

## 9. Ответственность, обновление и контроль

9.1. **Владелец страницы** отвечает за фактическую точность; **автор изменения** — за одновременное обновление кода и документации; **ревьюер** — за полноту и воспроизводимость описанных действий.

9.2. Документация ОБЯЗАТЕЛЬНО обновляется в том же pull request, что и изменение поведения системы. Отдельный последующий PR возможен только по оформленному исключению с ответственным и сроком.

9.3. Обязательные триггеры обновления:

| Изменение в продукте | Что обновить |
|---|---|
| Новый или изменённый API | Контракт OpenAPI, справочник API, примеры, миграции клиентов |
| Новая переменная среды | `.env.example`, справочник конфигурации, развёртывание |
| Изменение архитектуры | Схема архитектуры, ADR, ограничения |
| Изменение релизного процесса | Развёртывание, откат, runbook |
| Изменение поведения пользователя | README/руководства, примеры, CHANGELOG |
| Уязвимость или изменение доступа | SECURITY, правила эксплуатации, рекомендации по миграции |
| Новый способ тестирования | `docs/development/testing.md`, CI-проверки |

9.4. РЕКОМЕНДУЕТСЯ включить в CI проверку Markdown, внутренних/внешних ссылок, орфографии/терминов, синтаксиса примеров, соответствия OpenAPI, отсутствия секретов и сборки документационного сайта. Неприменимые проверки исключаются явно.

9.5. РЕКОМЕНДУЕТСЯ пересматривать критичную эксплуатационную документацию после каждого существенного изменения и не реже одного раза в квартал; остальные разделы — при изменениях и плановом обзоре, например раз в полгода.

9.6. «Готово» для изменения продукта означает, что техническая документация отражает поставляемую версию, примеры проверены, ссылки работают, а заинтересованный владелец одобрил изменение.

## 10. Чек-лист приёмки документации

### Содержание
- [ ] Назначение проекта и целевая аудитория понятны без устного пояснения.
- [ ] Указаны требования, зависимости и поддерживаемые версии.
- [ ] Есть воспроизводимый быстрый старт с проверкой результата.
- [ ] Архитектура, зависимости и потоки данных соответствуют текущему коду.
- [ ] Публичные API и форматы ошибок документированы.
- [ ] Конфигурация описана с типами, значениями по умолчанию и примерами.
- [ ] Указаны ограничения, известные проблемы и условия безопасности.
- [ ] Описаны развёртывание, откат, диагностика и восстановление, если применимо.
- [ ] Изменения и несовместимости отражены в CHANGELOG/миграционных заметках.

### Оформление и ясность
- [ ] У страницы один H1; заголовки логичны и последовательны.
- [ ] Файлы названы единообразно; навигация и ссылки работают.
- [ ] Термины и сокращения определены и используются последовательно.
- [ ] Инструкции написаны конкретно, без неоднозначных шагов.
- [ ] Код и команды имеют метку языка, контекст и ожидаемый результат.
- [ ] Примеры не содержат секретов или реальных персональных данных.
- [ ] Схемы подписаны, читаемы и соответствуют архитектуре.
- [ ] Даты, часовые пояса, единицы измерения и версии указаны явно.

### Актуальность и проверка
- [ ] Документация относится к целевой версии релиза.
- [ ] Примеры команд, запросов и ответов проверены.
- [ ] Документация обновлена в одном PR с соответствующим кодом.
- [ ] Пройдены доступные проверки CI: Markdown, ссылки, сборка, секреты.
- [ ] Назначен владелец ключевых разделов.
- [ ] Архитектурные решения оформлены ADR, если это необходимо.
- [ ] Ревьюер подтвердил полноту и воспроизводимость.

### Эксплуатация и безопасность
- [ ] Описаны безопасное хранение секретов и настройки доступа.
- [ ] Для опасных операций указаны риск и условия выполнения.
- [ ] Указаны health checks, метрики/логи и порядок эскалации.
- [ ] Для критичных изменений предусмотрен план отката.
- [ ] Документация доступна тем ролям, которым она необходима.

## 11. Критерии приёмки и исключения

Изменение документации **не принимается**, если оно содержит недостоверные команды, раскрывает секреты, противоречит фактическому API, не позволяет выполнить критическую процедуру или не прошло обязательные проверки проекта.

Для неприменимых требований допускается пометка **N/A** с причиной. Исключения из обязательных требований фиксируются в PR или реестре решений с указанием владельца, причины, риска и срока пересмотра. Этот стандарт следует дополнить организационными SLA, матрицей ответственности и требованиями к защите информации при его внедрении.

## 12. Основа стандарта: первоисточники и руководства

Перечень используется как методическая база, а не как утверждение, что все перечисленные документы являются обязательными нормативными актами. Актуальность редакций и доступность адресов требуют проверки перед официальным утверждением стандарта.

1. [Google Developer Documentation Style Guide](https://developers.google.com/style) — стиль технических текстов.
2. [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/) — ясность и терминология.
3. [Diátaxis](https://diataxis.fr/) — разделение документации по назначению.
4. [GitHub Docs Style Guide](https://docs.github.com/en/contributing/writing-for-github-docs/style-guide) — правила подачи и структуры.
5. [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) — смысл нормативных слов MUST/SHOULD/MAY.
6. [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) — уточнение трактовки нормативных слов.
7. [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) — описание HTTP API.
8. [PEP 257](https://peps.python.org/pep-0257/) — соглашения по Python docstrings.
9. [C4 Model](https://c4model.com/) — архитектурные диаграммы.
10. [Architecture Decision Records](https://adr.github.io/) — фиксация решений.
11. [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) — ведение истории изменений.
12. [Semantic Versioning](https://semver.org/) — правила версионирования при выборе SemVer.
13. [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) — ориентиры проверок безопасности.
