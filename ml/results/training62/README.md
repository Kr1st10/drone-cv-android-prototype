## Размер объекта и мобильное исполнение

Группы — √(w×h) рамки в пикселях канонического кадра до изменения размера: <16, 16–<24, 24–<30, ≥30. Например, при letterbox 1920×1080→640×640 коэффициент 1/3: квадрат 20×20 px отображается как примерно 6.67×6.67 на входе модели (отступы не увеличивают размер). 20 px в уже переразмеренном AOD4 1024×1024 — не обязательно 20 px в исходном видео. Апскейл не возвращает отсутствующую детализацию; большее входное разрешение не гарантирует лучшего качества. Физический зум, размеры preview и ImageAnalysis нужно отдельно измерить на устройстве.

QNN не проверен: локальный ORT предоставляет только AzureExecutionProvider и CPUExecutionProvider. Поддержка ONNX отдельных операторов не гарантирует разбиение целой графовой модели на HTP; QNN HTP в документации требует квантованную модель и совместимые операторы/версии SDK. Реальная проверка — отдельный этап на подходящем Qualcomm окружении, с проверкой покрытия графа и отсутствия незамеченного CPU fallback, а также качества после квантования. См. https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html . Никаких заявлений о работе на NPU Xiaomi 17 Pro.

## Подготовка данных и обучение

1. Следуйте `ml/results/dataset45/README.md` и `PROTOCOL.md`: импорт исходных кадров без ресайза, ручная ревизия всех дронов/негативов, права и реальное происхождение каждого видео, review разметки и дублей, группировка по source/sequence/video, реальные reference-манифесты. Декларации человека и отсутствие хеш-совпадений не являются доказательством независимости. Защитите доступ к final test организационно. При утечке нужен новый holdout. Птицы и самолёты используются как размеченные hard negatives в одноклассовом обучении; смешанные кадры должны содержать все размеченные дроны.
2. Установите зафиксированные зависимости `ml/requirements.txt` (для обучения на GPU понадобится совместимая сборка torch 2.6.0, CUDA и документирование среды). Подготовьте утверждённый манифест и frozen lock из dataset45. Нужны непустые train/validation/test, причём train и validation должны содержать размеченных дронов; укажите тот же набор `--reference`, что при freeze. Отсутствие references явно документируйте, не называйте независимость доказанной.
3. Получите baseline PT через `python ml/scripts/fetch_and_export.py --skip-export`; скрипт проверяет источник и SHA `337390e1018eaf815474c02e172a224425095466d4a5cd2dbd11301b0aa01b78`. Просмотрите `experiment.json` — это **первичная фиксированная гипотеза**, 10 эпох, seed 62, 640, AdamW; остальные default-параметры фиксируются используемой версией Ultralytics и `args.yaml`. Не считать её оптимальной до validation.
4. Вне папки датасета и репозитория выполните:

```bash
python -m ml.train62 --manifest /data/dataset/approved.json --lock /data/dataset/frozen.json \
  --reference /data/reference/manifest.json --checkpoint ml/weights/best.pt --output /data/run62-01
# Только после review команды, данных, лицензий и вычислительных ресурсов:
python -m ml.train62 --manifest /data/dataset/approved.json --lock /data/dataset/frozen.json \
  --reference /data/reference/manifest.json --checkpoint ml/weights/best.pt --output /data/run62-02 --device 0 --run
```

Первый вызов только materialize, никакого обучения. Каждый output обязан быть новым. Перед копированием проверяются stage45 хеши/разметка, допуск, lock и его references; копируются только train и validation, test не попадает в data.yaml. `run.json` фиксирует хеши конфигурации, checkpoint, манифеста и lock, версии и статус; при успехе SHA `best.pt`, `last.pt`, `results.csv`, `args.yaml`. Чекпойнты, локальные данные и журналы могут быть крупными или ограниченными лицензией — не добавляйте их в GitHub. Не гарантируется bitwise-детерминизм различных GPU, backend и библиотек.

Для YOLO11n сначала отдельно получите официальные веса, зафиксируйте URL, неизменяемую ревизию/релиз, SHA и права. Создайте отдельную согласованную конфигурацию с теми же данными, seed, оптимизатором и условиями; нужен одноклассовый drone checkpoint и статический ONNX с совместимым выходом. Не приписывайте ему метрики s.

## Сопоставление на validation

Для каждого одноклассового ONNX 640 выполните в одинаковых условиях (фиксировать машину/нагрузку, потоки, порядок):

```bash
python -m ml.compare62 --manifest /data/dataset/approved.json --lock /data/dataset/frozen.json \
  --reference /data/reference/manifest.json --onnx /data/model.onnx --model-id baseline \
  --expected-sha256 ACTUAL_SHA256 --threads 2 --output /data/val-baseline.json
```

В JSON фиксируются SHA модели/манифеста/lock, пост-NMS рамки, 9 точек PR при confidence > порога (floor 0.05, NMS IoU 0.7, матч IoU ≥0.5; это усечённая кривая, а не полный AP), P/R, TP/FP/FN, size bins с N, FP на проверенных негативах и на bird/airplane-only сценах, геометрические пересечения FP с drone/bird/airplane GT. Геометрические категории не взаимоисключающие и не устанавливают причину FP; требуется визуальный аудит. Измерено время preprocessing+ORT+postprocessing без декодирования, 3 warm-up кадра; сравнивайте median/mean только при одинаковой среде, без переноса на Android. Одинаковые постобработка и matching обязательны, precision — по всем кадрам. Не подбирайте пороги или модель на test; фиксируйте решения по validation до единственной финальной оценки по `dataset45.evaluate` и сохраняйте независимый журнал допуска. Малые группы и коррелированные видеокадры ограничивают выводы.
