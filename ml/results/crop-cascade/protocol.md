# Офлайн-каскад YOLO11s и классификатора кропов

Каскад получает тот же исходный RGB-кадр, что и YOLO. Штатная модель
`yolo11s-drone-640.onnx` (SHA из [манифеста](../../model_manifest.json)) выполняет
один проход в ONNX Runtime CPU. Постобработка использует общий Python-эталон
проекта. При NMS IoU 0,7 каскад берёт до восьми рамок с YOLO score >0,05.
Для каждой рамки вырезается область из исходного RGB с контекстом 20% по
каждой оси, обрезается у края кадра и помещается в квадрат 48×48 с сохранением
пропорций. Ресайз использует area при уменьшении и bilinear при увеличении,
паддинг RGB 114, вход FP32 NCHW в диапазоне [0,1]. Кропы идут одним батчем в
три свёртки со stride 2 (12/20/24 канала), ReLU, AveragePool, линейный слой
и sigmoid. Итоговый score = `YOLO score × p_drone`. Порог применяется к
этому произведению. Каскад возвращает исходные координаты выбранных рамок.

Число кадров сильно превышает число независимых мест. |

Старые веса дообучений не использовались. Для нового опыта переиспользованы
импорт Halmstad/Flying, разметка DUT, дедупликация VDD по исходному имени,
группы 6.4, инструменты dataset45 и Python-постобработка. Исходные архивы
скачиваются по закреплённым адресам с проверкой SHA-256. Негативный фон
выбран детерминированно из COCO val2017 без меток птицы, самолёта и воздушного
змея. В COCO отсутствует класс `drone`, поэтому фон оценивается по слабой
разметке. Медиа и веса остаются локально согласно правилам проекта.

## Как исключались пересечения

- Train и validation берутся из собственных Halmstad-видео. Все кадры одного
  видео и связанного сценового кластера 6.4 принадлежат одной части. Внешние
  Halmstad-видео и видео из sealed test не декодируются. Разметка и порог
  подбираются без доступа к результатам внешней оценки.
- Внешняя оценка держит DUT val целиком на стороне проверки, вместе с VDD
  (одна площадка, по одной копии каждого оригинала), Flying Object (одна
  камера в Токио) и COCO (только фон). Видео DUT из train/официального split
  6.3 не используются для классификатора. Зарезервированные записи UAVDB и
  Anti-UAV300 остаются закрытыми.
- Импорт сверяет идентификаторы групп, видео и SHA видео. Дубликаты кадров
  проверяются по SHA файла и RGB-пикселей, а похожие — по dHash ≤4, разнице
  средних RGB ≤5/255 и средней пространственной разнице RGB thumbnail 32×32
  <5/255. Совпавшие held-out группы исключаются целиком. Итоговый аудит
  отклонил 128 предварительных dHash-кандидатов по пространственному
  расхождению. Подтверждённых совпадений по этому протоколу 0.
- Это исключает пересечения по известным группам и найденным дубликатам.
  У DUT detection val нет надёжной карты исходных видео и сцен. Состав
  предобучения штатной YOLO опубликован без точного списка кадров. Место
  Halmstad train содержит все положительные обучающие кропы. У Flying и VDD
  по одной площадке. Внешние датасеты уже фигурировали в исследованиях
  проекта. Эти ограничения не позволяют трактовать пилот как независимую
  полевую приёмку или строить доверительные интервалы по отдельным кадрам.

## Сравнение

Основная точка — штатный live-порог YOLO 0,50, NMS 0,7. Бюджет считается
по числу FP-рамок при жадном взаимно однозначном сопоставлении с GT по
IoU ≥0,5. Для каскада на validation выбирается минимальный порог, который
укладывается в бюджет исходной YOLO. При одинаковом score остаётся только
целая группа рамок. Порог фиксируется и применяется к внешней выборке.
Дополнительно считаются:

- Диагностическая точка на внешних кадрах при том же бюджете исходной YOLO.
  Она показывает качество ранжирования. Такой порог уже подогнан под
  внешний набор.
- Тот же расчёт бюджета только по кадрам без размеченного дрона. Он показывает
  обмен ложных тревог на ухудшение или улучшение локализации на позитивных
  кадрах. FP на классах считаются и по типу кадра, и по пересечению с рамкой
  класса.
- Precision/Recall при IoU 0,5 и 0,3, Recall по √(w·h) GT после letterbox 640,
  медиана IoU совпадений, FP с IoU от 0,1 до границы совпадения, дубли,
  FP вдали от GT и верхняя граница по наличию post-NMS рамки до и после
  ограничения top-8. Смена порога не исправляет координаты отдельных рамок.

Для обучения взяты только post-NMS кандидаты с train. Метка `дрон` даётся
при IoU ≥0,3 либо при IoU ≥0,1 и взаимном попадании центров в рамки. Сомнительные
кропы около GT исключаются, остальные становятся негативами, включая кандидатов
вне размеченных объектов. На кропах применялось горизонтальное отражение.
Классы балансируются, вклад кадров из одной группы смягчён весом 1/√n.
Выполнено 20 фиксированных эпох CPU, AdamW 0,002, seed 65, batch 64. Выбор
эпохи по validation не проводился. ONNX opset 17, динамический batch, проверка
графа и сравнение PyTorch/ONNX на batch 1/2/8/32 входят в обучение.

## Результаты внешней проверки

3 072 кадра, 1 316 GT. Halmstad train содержит 1 662 кадра из 37 групп,
validation — 299 кадров из 10 групп. Обучено на 873 положительных
post-NMS кропах из **одной** группы и 1 502 отрицательных из 36 групп.
42 неоднозначных кандидата пропущены. Экспорт дал 6 957 обучаемых параметров,
29 319 байт и максимальное расхождение PyTorch/ONNX 2,38×10⁻⁷.
Повторное обучение на тех же кандидатах воспроизвело ONNX побайтово.

| Точка | TP | FP все | FP без дрона | Recall@0,5 | Precision@0,5 | Recall@0,3 | FP с IoU 0,1–<0,5 |
|---|---:|---:|---:|---:|---:|---:|---:|
| YOLO score >0,50 | 541 | 1 555 | 1 328 | 41,1% | 25,8% | 53,6% | 180 |
| Каскад, порог 0,07760 из validation по всем FP | 429 | 644 | 346 | 32,6% | 40,0% | 43,0% | 171 |
| Каскад, порог 0,03357 из validation по FP без дрона | 527 | 1 161 | 649 | 40,0% | 31,2% | 52,7% | 248 |
| Каскад, диагностически при тех же 1 555 FP | 570 | 1 555 | 921 | 43,3% | 26,8% | 57,1% | 283 |
| Каскад, диагностически при тех же 1 328 FP без дрона | 613 | 2 064 | 1 328 | 46,6% | 22,9% | 61,3% | 314 |

В точке с 1 555 FP это **+29 TP**. На VDD получено 427/719 вместо 386/719,
на DUT — 143/597 вместо 155/597. На кадрах Flying Object с самолётами
FP-рамок стало 38 вместо 150, с вертолётами 730 вместо 1 118. На кадрах с
птицами FP-рамок стало **68 вместо 41**, на COCO — **85 вместо 19**.
В той же точке FP на кадрах с дроном вне GT (IoU <0,1) выросли с 47 до 326.
Медиана IoU правильных совпадений 0,719 → 0,717. Распределение ошибок
меняется вместе с порогом и источником.

| Размер GT на входе 640 | YOLO 0,50 | Каскад, порог из validation по всем FP | Каскад, те же 1 555 FP | Верхняя граница top-8 при 0,05 |
|---|---:|---:|---:|---:|
| <8 px | 25/319 | 27/319 | 31/319 | 36/319 |
| 8–<16 px | 113/241 | 73/241 | 96/241 | 126/241 |
| 16–<24 px | 27/56 | 25/56 | 33/56 | 38/56 |
| 24–<30 px | 34/81 | 32/81 | 44/81 | 48/81 |
| ≥30 px | 342/619 | 272/619 | 366/619 | 424/619 |
| **Всего <16 px** | **138/560** | **100/560** | **127/560** | **162/560** |

Верхняя граница предполагает идеальную фильтрацию рамок и учитывает наличие
хотя бы одного кандидата с IoU ≥0,5 на GT. Из 560 дронов <16 px у 398
такого кандидата нет даже при пороге 0,05. Лимит top-8 отсёк хвост на одном
кадре из 3 072, без потери верхней границы. 92% кадров получили хотя бы
один кроп, 89% кадров получили не более двух.

**Решение — текущий каскад отклонить для Android.** Фиксированный порог
снизил Recall, диагностическая прибавка при том же числе FP пришлась
преимущественно на VDD и сопровождалась потерей дронов <16 px и ростом
ложных тревог на птицах и фоне. Возвращаться к гипотезе стоит после сбора
нескольких независимых съёмок с дронами <16 px, птицами, самолётами и
подтверждёнными пустыми сценами. Сцены и исходные видео должны быть
разведены между обучением, калибровкой и итоговой проверкой.

## Добавочная стоимость

Замеры на MacBook Air M4, macOS arm64, ONNX Runtime 1.31.1 CPU.
На 3 072 кадрах с общим YOLO-инференсом добавка каскада над исходным NMS
составила **0,10 мс p50 и 0,84 мс p95**. Включены более низкий порог NMS,
кропы, тензор и второй ONNX. Декодирование изображения, запуск ORT и
интерфейс в замер не вошли. В отдельном прогретом микробенчмарке кроп
и классификация дали 0,10 мс p95 для одного и 0,78 мс p95 для восьми.
Инициализация классификатора в отдельном процессе заняла 1,60 мс.
Максимальная вычислительная работа модели — около 0,65 млн MAC на кроп,
или 5,23 млн при восьми кропах.

Файл модели весит **28,6 КиБ**. Полный батч FP32 требует **216 КиБ**,
без учёта активаций, промежуточных копий и арены ORT. В прогретом процессе
с уже загруженной YOLO дополнительный классификатор и прогрев батчем 8
увеличили текущий RSS на 176 КиБ в этом замере. RSS учитывает резидентные
страницы и переиспользование аллокатора. В отдельных процессах общий RSS
двигался на несколько МиБ в обе стороны между повторами. Эти числа
описывают macOS, а размер файла и входного тензора переносятся на Android
при той же реализации. Реальные p95 и PSS Android остаются неизвестны.

При возобновлении работы достаточно второй последовательной сессии
в имеющемся ONNX Runtime CPU, одного вызова на батч и переиспользуемого
тензора из уже захваченного RGB. Для оценки на Xiaomi 17 Pro нужны
сопоставимые A/B прогоны с прогретой камерой, разбиение p50/p95 по числу
кропов и прирост PSS. [Документация ONNX Runtime для мобильных платформ](https://onnxruntime.ai/docs/tutorials/mobile/)

## Воспроизведение

Проверено на macOS arm64 и Python 3.13. Для полного прогона нужны сеть
для получения данных (~1 ГБ архивов), около 3 ГБ на данные и отдельный
venv. После подготовки все команды инференса работают офлайн. Возьмите
готовый штатный ONNX по [инструкции проекта](../../../docs/getting-started.md#подготовить-модель)
и положите копию в `ml/data/cascade/yolo11s-drone-640.onnx`. Эксперимент
проверит его SHA автоматически.

```bash
python3.13 -m venv ml/data/cascade/venv
source ml/data/cascade/venv/bin/activate
python -m pip install -r ml/cascade/requirements.txt
export OPENBLAS_NUM_THREADS=1

run_dir=ml/data/cascade
manifest="$run_dir/pilot-v2/manifest.json"
yolo="$run_dir/yolo11s-drone-640.onnx"
verifier="$run_dir/crop-verifier.onnx"

python -m ml.cascade.prepare --raw "$run_dir/raw" --output "$run_dir/pilot-v2" --download
python -m ml.cascade.run mine --manifest "$manifest" --yolo "$yolo" --output "$run_dir/mined-final.json"
python -m ml.cascade.train --manifest "$manifest" --mined "$run_dir/mined-final.json" --output "$verifier"
python -m ml.cascade.run calibrate --manifest "$manifest" --yolo "$yolo" --classifier "$verifier" --output "$run_dir/calibration.json"
python -m ml.cascade.run evaluate --manifest "$manifest" --yolo "$yolo" --classifier "$verifier" --calibration "$run_dir/calibration.json" --output "$run_dir/evaluation.json"
python -m ml.cascade.benchmark --manifest "$manifest" --yolo "$yolo" --classifier "$verifier" --output "$run_dir/benchmark.json"
```

Каталог `pilot-v2` для нового импорта должен отсутствовать. В локальной
рабочей копии манифест, оба ONNX и результаты уже подготовлены. В команде
ниже скрипт загружает готовый ONNX классификатора, читает зафиксированный
порог из JSON и выводит реальные рамки двух вариантов на кадрах VDD и
Flying Object. Локальный сценарий доступен сразу после выполнения работы.

```bash
sh ml/data/cascade/demo/run.sh
```

Для своего кадра из корня проекта:

```bash
source ml/data/cascade/venv/bin/activate
run_dir=ml/data/cascade
threshold=$(python -c 'import json,sys; print(json.load(open(sys.argv[1]))["thresholds"]["all_fp"])' "$run_dir/calibration.json")
python -m ml.cascade.run infer --yolo "$run_dir/yolo11s-drone-640.onnx" \
  --classifier "$run_dir/crop-verifier.onnx" --threshold "$threshold" /путь/к/кадру.jpg
```

JSON результата хранит рамки как `[x1,y1,x2,y2,yolo_score]` и
`[x1,y1,x2,y2,yolo_score,p_drone,fused_score]`. Координаты относятся
к декодированному исходному RGB. Время не включает декодирование файла.
