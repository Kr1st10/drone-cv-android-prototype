## 5. Интеграция CameraX и ORT (2026-11-02)

Проверены официальная [configuration](https://developer.android.com/media/camera/camerax/configuration),
[analysis](https://developer.android.com/media/camera/camerax/analyze) и точные исходники
[camera-core 1.4.1](https://dl.google.com/dl/android/maven2/androidx/camera/camera-core/1.4.1/camera-core-1.4.1-sources.jar),
[camera-view 1.4.1](https://dl.google.com/dl/android/maven2/androidx/camera/camera-view/1.4.1/camera-view-1.4.1-sources.jar).

- UseCaseGroup + PreviewView.viewPort/FILL_CENTER гарантируют одинаковый видимый FOV после crop и rotation.
  Для задней камеры normalized upright-crop координаты непосредственно отображаются на размеры PreviewView;
  отдельный экспериментальный CoordinateTransform не нужен для текущего ограниченного пути.
- ImageAnalysis.java версии 1.4.1 определяет RGBA byte order как **R,G,B,A**. В guide analyze при проверке
  был указан противоречащий A,R,G,B; реализация опирается на версионные API/исходники и channel/stride tests.
- KEEP_ONLY_LATEST вместе с синхронным analyzer ограничивает работу текущим/последним кадром без отдельной очереди.
  ImageProxy.close обязателен на всех путях. Физическое совмещение на конкретном телефоне всё ещё требует QA.
- Использован CPU ORT sequential, intra-op=2/inter-op=1, spinning=0 согласно
  [thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).
  Это ограничивает конкуренцию и idle spin; оптимальность 2 потоков на целевом телефоне **не измерена**.
  XNNPACK/NNAPI/GPU остаются кандидатами для отдельного сравнения, ускорение не заявляется.
- RGBA читается построчно с crop/stride в переиспользуемый ARGB IntArray, поворот совмещён с letterbox
  в прежнем препроцессоре. Анализ предпочитает 640×480: это экономит копирование относительно HD, но
  конкретное влияние на малые объекты и частоту кадров ещё не измерено. CameraX может согласовать другой размер.

### Интеграционные риски UI, обнаруженные CI

2026-11-02, API 29 x86_64, [первый emulator run](https://github.com/Kr1st10/drone-cv-android-prototype/actions/runs/41435816804):
последовательные camera rebind и timeout; затем stack `StateFlow.setValue → ApplyingContinuationInterceptor →
TestMonotonicFrameClock.measureAndLayoutForTest` на `drone-inference`, concurrent layout crash.
Это проверенный сбой тестового Compose dispatcher, не доказательство такого же thread dispatch в обычной Activity.
UI collector закреплён на Dispatchers.Main.immediate. Размер панели зафиксирован независимо от статистики,
чтобы убрать возможность feedback layout→rebind→invalidate; точная причина первого rebind loop ещё проверяется.
Android regression ждёт ≥3 результатов в одной активной сессии. Переносы лямбд в отдельные функции не нужны:
проверка javap показала стабильные rememberComposableLambda/state holder.

Повторный [CI run 41439862685](https://github.com/Kr1st10/drone-cv-android-prototype/actions/runs/41439862685),
код `478f2b7`: 9/9 Android-тестов passed, включая ≥3 последовательных результата и lifecycle/rotation;
layout crash не повторился. Bind-log содержит стабильные 1080×734 (rotation 0) и 1164×753 (rotation 1/3)
в соответствующих сценариях, без прежнего непрерывного пересоздания. Это подтверждение эмуляторной интеграции,
не измерение FPS/нагрева телефона и не проверка качества на реальном дроне.


## 6. Эксперимент SAHI (этап 4.1, 2026-11-02)

Скрипты `ml/scripts/sahi_experiment.py`, `sahi_examples.py`; отчёт и таблицы `ml/results/sahi/REPORT.md`.
Официальный `obss/sahi` 0.14.0 вокруг прежнего ONNX-пайплайна (SHA-256 `b4867481…`), одна модель и одни кадры.
Выборка: 360 позитивов pathikg test (383 GT, стратифицировано по размеру, **не независимо**) + 200 негативов COCO.
Среда: Python/ORT CPU, 2 vCPU sandbox — не телефон.

- Лучший режим — слайс 416, overlap 0.2, + full-frame, GREEDYNMM/IOS 0.5. При conf 0.5: P на позитивных кадрах 0.929 → 0.934, P по всей выборке 0.775 → 0.694 (считая детекции на COCO-негативах за FP),
  R 0.755 → 0.812 (+24/−2 GT), F1 на позитивах 0.833 → 0.869. Recall <16 px 0.695 → 0.737; 16–24 px 0.792 → 0.806 (≈ без изменений).
- Негативы с ≥1 ложной детекцией (conf 0.5): hard 37 → 60, random 17 → 37 из 100. Слайс 320 — ещё хуже (68 / 49).
- Время при conf 0.25: baseline 102.7 мс (прогон 2) → 523.2 мс (×5.09); слайс 320 + full — 762.2 мс (×7.42). Все коэффициенты относительно одного baseline; измерения разных прогонов шумные.
- Слияние IOS иногда поглощает маленькую верную рамку большой ложной рамкой из слайса; IOU устраняет это, но
  оставляет дубли фрагментов (40 FP-дублей, P 0.835). Без full-frame прохода крупные дроны теряются (R ≥96 px 0.733).
- **Решение:** SAHI в живой Android-режим не внедрять; рост recall мал, у ~20 px почти нулевой, а ложные тревоги
  на сценах без дронов почти удваиваются при ×5 стоимости. Отсутствие существенного улучшения у ~20 px зафиксировано.
- Дальше: независимый набор с телефона; один инференс с бо́льшим входом тех же весов; ROI-SAHI / «глубокий скан»
  фото; подавление FP; слияние с ограничением отношения площадей.

Следующий шаг — независимые телефонные сцены и вручную проверенные объекты 10–30 px.

## 9. Аудит ошибок AOD 4 (этап 4.4, 2026-11-02)

Полный протокол, визуальные замечания и воспроизведение — `ml/results/aod_audit/REPORT.md` и `README.md`. Сверка архивной разметки, SHA и размеров 160 кадров, классов модели и независимого TP/FP/FN подтвердила расчёт 640 **относительно исходных меток**, а не их фактическую полноту. Найден и исправлен пограничный случай `IoU == 0.5`: ранее добавочный epsilon мог его исключить; добавлены регрессионные тесты. Пересчёт сохранённых округлённых рамок 640/960/SAHI не изменил покадровые метрики 4.3; 4.1/4.2 в этом аудите заново не пересчитывались.

Из 75 FP 640 восемь находятся на bird-only кадрах, 28 на airplane-only; по визуальному осмотру это реакции на птиц и самолёты. На позитивных 36 рамок частично пересекают drone GT при IoU 0.1–<0.5, ещё три не пересекают или почти не пересекают GT; это геометрическая, а не окончательная семантическая классификация. Вероятны локализационные расхождения и неполная разметка, но необходима проверка источников и политики bbox. Найден спорный отрицательный кадр с похожим на искусственную птицу объектом и три сомнительные аннотации <16 px; исходные метки не меняли. Все 80 негативов проверены на обзорных изображениях, что не доказывает отсутствие неразмеченных дронов.

На той же выборке при conf >0.5 P/R = 0.279/0.276 (29/75/76), при >0.75 — 0.300/0.171 (18/42/87): небольшое повышение precision ценой 11 из 29 TP. У 68 из 76 FN нет post-NMS кандидата с IoU ≥0.5 выше 0.05; это не означает нулевой confidence модели. Пороги исследовательские, не проверены независимо. Продолжение: согласовать политику меток, собрать разделённые по видео независимо проверенные малые дроны и сложные негативы, затем сравнить контролируемое дообучение существующей модели с фиксированным baseline на отдельном test. Перенос в Android и обучение в этапе 4.4 не выполнялись.

## 13. Реальные данные DUT-Anti-UAV: baseline и дообучение (этап 6.3, 2026-11-03)

- Подробности и команды: `ml/results/dut63/README.md`. Официальные split DUT-Anti-UAV detection **не независимы**: 133 train-кадра визуально из тех же сцен, что val (dHash 0). Перед любым использованием нужен сценовый фильтр (у нас — исключение train с Хэммингом ≤ 10 до val). Val-шард 600 кадров ≈ 50 сцен; метрики сопровождаются бутстрепом по кластерам.
- Текущая YOLO11s на DUT val (1920×1080, 640): P 0.436 / R 0.288 при conf 0.25; recall <16 px 4.8 %, 16–<24 px 14.4 %, ≥30 px 60 %. Значительная доля ошибок — несоответствие ширины рамок плотной разметке DUT (при IoU 0.3 R 0.513), поэтому метрики зависят от стиля разметки источника.
- 3-эпоховое CPU-дообучение на 934 отфильтрованных train-кадрах повысило P/R при IoU 0.5 (0.669/0.403), но снизило recall при IoU 0.3 (0.457 против 0.513) и не улучшило <16 px: в train почти нет малых дронов. Это адаптация к стилю рамок, а не доказанное улучшение обнаружения. Следующий шаг: train с малыми объектами и сценовой группировкой, подтверждённые негативы (птицы/самолёты), закрытый независимый test, GPU-обучение по подготовленной конфигурации и проверка на устройстве.
- В DUT train встречаются стоковые изображения с водяными знаками (gettyimages): Apache-2.0 репозитория не подтверждает права на все кадры; изображения не распространять.

## 14. Маленькие дроны и FP на птицах/самолётах: Halmstad + Flying Object (этап 6.4, 2026-11-03)

- Подробности, хеши и команды: `ml/results/real64/README.md`. Открытые данные: Halmstad Drone-detection-dataset (CC0-1.0, видимые видео 640×512; 49 видео с YouTube — только локальная оценка) и sekilab Flying Object (MIT, без дронов, одна сцена — только негативы). CSIO YOLOBirDrone и WOSDETC Drone-vs-Bird требуют форм/соглашения от пользователя и не использовались.
- Маленьких дронов в доступных открытых данных почти нет: из 1105 рамок дронов <16 px — 10, 16–<24 — 234. Рамки Halmstad свободные (видимый объект часто вдвое меньше рамки), поэтому IoU-метрики пессимистичны; дополнительно считаются отклик (центр в 3× окрестности GT) и центр внутри GT. Цифровой зум и апскейл эту проблему не решают: деталей в пикселях нет.
- Почти-дубликатная группировка показала, что 101 из 225 собственных видео Halmstad сняты в одном месте; групп с дронами всего 7. Split групповой (test запечатан, 3 группы с дронами), но независимость оценки ограничена.
- Baseline YOLO11s: отклик на дроны ≥24 px ≈98 %, 16–<24 px 75 % (conf 0.25), <16 px 0/6; R@IoU0.3 0.44, R@IoU0.5 0.14 (стиль рамок). **Главная проблема — FP на других летящих объектах**: на 81–95 % кадров с птицами, самолётами или вертолётами без дрона есть ложное срабатывание (conf 0.25), на 60–87 % при conf 0.5; на независимой камере Flying — 90–94 %. Модель фактически детектирует «летящий объект».
- Ограниченное CPU-дообучение (3 эпохи, только train-группы собственных видео, птицы/самолёты/вертолёты — фон) снизило долю FP-кадров до 0–15 %, но сжало уверенности (≤0.44), уменьшило отклик на 16–<24 px с 49 до 6 из 91 и обнулило recall на DUT val (0/600 при conf 0.25). Кандидат отклонён. Следующий шаг: больше мест съёмки с дронами, включая 10–30 px на целевых телефонах; негативы смешивать с исходными данными, низкий lr или заморозка backbone; отдельная голова/классификатор «дрон / птица / самолёт» на кропах — проверить отдельно с учётом экспорта ONNX/QNN (без новых операторов, допускающих квантование).

- Реально получены: UAVDB (Zenodo, фактически CC BY-NC-SA 4.0 через CenekAlbl), Anti-UAV300 (изображения без лицензии — только исследование), UAV-CB (CC BY-NC 4.0), VDD с Zenodo (Roboflow «Private», 717 уникальных из 2145 — только eval), Cranfield synthetic (CC-BY-4.0, только статистика), Halmstad-негативы (CC0), DUT val, pathikg replay. MMAUD и другие источники птиц/самолётов не исследовались.

Независимых мест мало: UAVDB — одно место (4 полёта, 17 камер), Anti-UAV — одна площадка (27 сессий за 2 дня), UAV-CB — одна площадка (10 сцен), VDD — одна площадка. Нового места, которое можно и обучать, и валидировать, нет: validation UAVDB и Anti-UAV — новый полёт/день на том же месте. Anti-UAV и UAV-CB малы только из-за 640 (native ≥30 px у 99 % / 93 %).
- Утечки: побайтовых дубликатов между split 0; dHash + миниатюры дают 17320 «похожих» пар — однотонное небо и тот же фон статических камер, копий кадров агентская проверка не нашла. Официальные train/val Anti-UAV делят сессии, а VDD раскидывает копии по split — их официальные разбиения непригодны.
- Baseline (conf 0.25, R@IoU0.3): UAVDB d1 0.995 (включая <8 px — чистое небо, контрастный гексакоптер), Anti-UAV 26 сент. 0.63 (<16 px 0/42), UAV-CB 0.31, DUT 0.51, VDD 0.68, pathikg 0.99; ложные срабатывания на 98–100 % кадров Halmstad с птицами/самолётами/вертолётами.
- Небольшое дообучение (1600 изображений, freeze=10, lr0 1e-4, без mosaic, 2 эпохи, `last.pt`, 0.66 ч CPU): Anti-UAV следующего дня 0.63 → 0.94 (<16 px 0 → 28/42), но FP на пустых кадрах 0.09 → 0.30; UAV-CB +0.045 при падении precision 0.57 → 0.36; VDD 0.68 → 0.48, DUT при conf 0.5 0.46 → 0.33, pathikg 0.99 → 0.96 (<16 px 0.96 → 0.83); FP Halmstad 0.98 → 0.71. **Кандидат отклонён**: выигрыш — подстройка под ту же площадку, чувствительность на других сценах падает.
- Вывод: проблема не в количестве малых рамок, а в числе независимых мест и камер. Следующий шаг — собственные записи на целевых телефонах в нескольких местах (10–30 px, птицы/самолёты в тех же кадрах) с групповым split по месту; публичные наборы использовать для eval и в смеси с replay; рассмотреть вторичный классификатор «дрон / не дрон» на кропах для подавления FP вместо дообучения детектора.
