# Пилот YOLO на неподвижной фотографии

Откройте [анализатор](index.html) в браузере. Он работает локально, включая открытие с диска. Для показа фотографии и задания эквивалентной дальности используйте [лабораторный стенд](../gallery.html). Запишите название эталона и фото, ракурс, фактическую эквивалентную дальность по калиброванной геометрии, расстояние до экрана, фон, устройство и камеру с зумом. Положение телефона, фотографию, масштаб, фон и порог держите постоянными.

1. На Android выберите режим «YOLO». После стабилизации заранее задайте начало серии, в секундах от старта диагностики. Если условия выставлены до записи, оставьте 0. Запустите диагностику и дождитесь окончания показа. При медленном детекторе набор 20 кадров может занять больше 20 секунд.
2. Выгрузите **диагностический отчёт** Android (JSON или NDJSON), выберите его на странице и внесите условия. Порог берётся из метаданных журнала. При отсутствии поля можно внести известный порог вручную, с указанием источника в экспорте.
3. Проверьте число отобранных кадров и выгрузите CSV или JSON. Отчёт диагностики сохраните отдельно.

## Правило отбора

Формат определяется по содержимому файла. Для JSON метка отбора — завершение инференса, для NDJSON — публикация результата. Берётся первая пригодная строка с указанного начала, затем первая пригодная строка не ранее чем через секунду после предыдущей отобранной. При равных метках действует порядок строк файла. Отбор ограничен 20 исходными кадрами и одной привязкой камеры.

### Диагностический JSON


В корневой схеме `schema_version=1` Android записывает в `frames[]` завершённые актуальные вызовы детектора, включая длительности пяти стадий. В режиме «YOLO» `target_signal` v2 содержит исход `detected` / `no_target`, идентификаторы источника и публикации, время входа исходного кадра в анализатор и confidence выбранного кандидата. Временная метка таблицы — `offset_ms` от начала записи **до завершения** YOLO.

Для исключения повторов сравниваются идентификатор публикации, время входа кадра и доступная метка экспозиции в рамках одного источника. Повторы исключаются и в случае, когда первое появление пришлось на интервал между отобранными кадрами или было до начала серии. Результат и confidence не влияют на порядок. Отклонённые и отменённые вызовы Android не записывает в ряд завершений. Записи `tracking.samples` и повторно используемый в них `last_yolo_confidence` не участвуют. Строки только с `detection_count` из режима сопровождения показывают наличие кандидата, но не имеют метки исходного кадра и не подходят для этой серии. Старые версии сигнала, отчёты только с таймингами и журналы A/B `dronecv-motion-android-1` не дают пригодных попыток для этого входа. Формат диагностики описан в [модели данных Android](../../../docs/reference/data-model.md#json-производительности-schema_version-1).

### NDJSON временной шкалы

Контракт сверён с [PR #35 @ 5081522](https://github.com/Kr1st10/drone-cv-android-prototype/tree/5081522). `header` задаёт начало и базу часов, `metadata` подтверждает режим `yolo` и порог. Допускается режим из заголовка, если он согласуется с метаданными. Пилот проверяет единство сессии, непрерывность `event_id`, корректность `session_end`, счётчики записи и признаки потерь, включая `recording_failure` после конца. При повреждении показывает доступные публикации с предупреждением о неполной записи.

У `state` чистого YOLO результат и исходный кадр находятся в одной строке. После завершения инференса контроллер публикует `result_source=yolo` и `reason=update` с текущим подтверждением и рамкой либо `reason=no_detection` с пустой рамкой. Оба исхода требуют совпадения `detector_frame_id` с `frame_id`. Повторы исходного кадра, начальный снимок, результаты кадров, вошедших в анализатор до записи, очистки таймером, LK и коррекции исключаются. Противоречивые строки с одним идентификатором исключаются. Для NDJSON смена поколения контроллера также завершает отбор.

`diagnostic_frame` содержит тайминги завершения в `System.nanoTime` и не содержит идентификатора кадра. Сопоставить его с `state` по этому контракту невозможно. Поэтому связь отмечается как `unknown`, а даже при 20 публикациях полнота серии по завершениям не подтверждается. Временная метка отбора — `publication_ns - start_ns` в `elapsedRealtimeNanos`. Для отбора, вычитания и проверки границ используются целые наносекунды. Экспорт сохраняет наносекунды и идентификаторы строками. `offset_ms` используется для отображения. Confidence отдельной публикации недоступен и остаётся `null`, порог из журнала сохраняется отдельно.

## Интерпретация и экспорт

В знаменатель входят только отобранные результаты с известным исходом. Доля равна числу кадров с кандидатом, делённому на число проверенных кадров. Для пустой серии она неизвестна. Кадры одной видеосессии коррелированы даже при секундном интервале. Импорт в «Измерить предел» по-прежнему означает одну подтверждаемую оператором проверку на файл.

Для автоматических TP/FN/FP нужны идентификатор исходного кадра, сам кадр или проверяемая ссылка на него, проверенная разметка присутствия/отсутствия цели и всех целевых объектов, полный список рамок YOLO с классами и confidence, включая явно пустой список, а также размеры и система координат кадра. Тогда можно сопоставить рамки один к одному по заранее заданному критерию, например порогу IoU. Диагностика v2 хранит центр кандидата. В NDJSON есть опубликованная рамка, но отсутствует независимая покадровая разметка. Для обоих входов TP/FN/FP, подтверждённый Recall и успешная дальность остаются недоступны.

В JSON `dronecv-yolo-pilot-1` есть сведения об исходном файле, условия, правило отбора, сводка, причины ограничения GT и список попыток. Confidence и доля записаны в шкале 0–1. CSV повторяет общие поля в каждой строке. Для пустой серии в CSV остаётся одна строка с условиями и сводкой, поле `attempt` пустое. Неизвестные значения записываются как `null` в JSON и пустые ячейки в CSV. JSON содержит исходный текст полей. CSV нейтрализует ввод, который электронная таблица может выполнить как формулу.
