# API ручных оценок движения

Модуль `motion-manual.js` доступен через CommonJS в Node и как `MotionManual` при подключении после `MotionAB` в браузере. Версия записей `manual-observation-v1` соответствует [ручному протоколу](MANUAL_PROTOCOL.md). Привязка к попыткам и выбор пары используют [серию A/B](AB_COMPARISON.md).

## Запись

- `read(observations, series, run)` возвращает копию оценки или пустую оценку по плану `run.scenario.laps`. Эталон должен иметь `run_id` зарегистрированной попытки и `series_id` серии. Для ретроспективной серии достаточно явной привязки попытки.
- `save(observations, series, run, patch)` проверяет поля и обновляет запись в переданном массиве по паре `series_id` и `run_id`. Начальное значение массива `[]`. Другие попытки и серия сохраняют свои данные. Переданные `laps`, `operator` и `coverage` заменяют поля целиком, остальные пропущенные поля сохраняют прежние значения. Неверное обновление вызывает `Error` до записи.
- `run_complete` отражает завершённость эталона, а `attempt_complete` отражает завершённость попытки в серии. `observation_complete` означает, что у всех показателей есть ответ, включая сомнение и неприменимость. `notes` хранит свободный комментарий.

| Поле | Значения при `status: 'known'` |
| --- | --- |
| `capture` | `before_hide`, `after_return`, `no_capture` |
| `laps` | Массив ответов по порядку плановых кругов. Для каждого круга `clean` или `violation` |
| `drops` | Целое неотрицательное число |
| `before_hide`, `after_return` | `true` или `false` |

Пустой ответ выглядит как `{ status: 'unanswered' }`. Известный ответ хранит `value`, в том числе `0` и `false`. Ответы `uncertain` и `not_applicable` требуют строки `reason`. Пропущенный участок круга отмечают `uncertain`, если оператор не видел нарушения. Круг, который так и не начался, отмечают `not_applicable`. При подтверждённом `no_capture` результат чтения показывает `drops` как `not_applicable`. Если подтверждение утрачено, модуль снова показывает независимый ответ оператора либо `unanswered`. Сохранённые ранее автоматически выведенные ответы распознаются по системной причине «Правильного захвата не было.». Новые ответы оператора отличимы даже при совпадении причины. Число срывов при подтверждённом `no_capture` вызывает ошибку.

### Полнота наблюдения

Оператор указывает `coverage.scenario_complete: true` после полного просмотра сценария и `coverage.after_return` для окна после появления. Для окна доступны `complete`, `partial` и `not_started`. Если охват неизвестен, поле можно пропустить.

Подтверждённый `no_capture` требует полного просмотра и отметки о завершении у попытки и эталона. Значение `after_return: false` требует полного просмотра окна. При известном `run.end_ms` модуль сверяет время остановки с границами фаз из плана. До скрытия отметка `before_hide` неприменима. До повторного появления отметка `after_return` неприменима, а поздний первый захват получает `uncertain`. После начала окна уже наблюдавшиеся положительные исходы сохраняются и при прерывании. Отрицательный исход при неполном или неизвестном охвате получает `uncertain` с причиной.

До первого показа цели захват получает `uncertain`, а число срывов получает `not_applicable`. Захват, который оператор увидел во время показа неподвижной цели, сохраняется. Круги начинаются с фазы движения. Их границы определяются по длительности движения и числу кругов из сценария. Круг, который к моменту остановки ещё не начался, получает `not_applicable`. Для круга, прерванного до конца, сохраняется подтверждённое нарушение или ранее указанная причина сомнения. В остальных случаях прерванный круг получает `uncertain`, в том числе при попытке отметить его чистым. Эти правила действуют при чтении, сохранении и правке примечания.

Если первый правильный захват отмечен после планового повторного появления, сохранение и импорт отклоняют отметку «Чистый» для любого круга, завершившегося к этому моменту. Стенд берёт границы из сценария сохранённого прогона и указывает номер круга и `run_id`. Пробелы наблюдения и ответы «Не удалось оценить» сохраняют свой смысл. Если противоречивая оценка уже есть в браузере, отчёт показывает её исходные ответы и причину, а разности по паре недоступны до исправления. При отказе импорта исходный JSON остаётся у оператора, а хранилище не меняется.

## Сравнение

`compare(observations, series, pairIndex, runs)` использует `series.selections` для заданной пары. Одинаковые объявленные значения образуют A/A. Для пар с разными значениями модуль сверяет выбранный фактор с фактическими данными каждой попытки.

Фото, геометрия экрана и план берутся из эталона стенда. Когда доступны сохранённые планы, для A/A и сравнения режима или сборки модуль сверяет их целиком. При сравнении скорости или ускорения сверяются геометрия маршрута, включая смещение и координаты участков, и остальные параметры плана. Объявленный фактор и производные параметры темпа допускают различия. Если план есть только у одной стороны, сравнение плана остаётся неподтверждённым. Производные различия режима учитываются по правилам A/B. Пустые строки, включая `build_id` из пробелов, считаются неподтверждёнными. В `operator` указывают фактические `device`, `build_id`, `mode`, `model_sha256`, `settings` (объект настроек приложения) и `route_visible: true` после проверки маршрута. Для установки можно подтвердить `setup_id`, `zoom`, `orientation`, `camera_config` и `distance_cm` в `operator`. Если подтверждения поля нет, используется записанное значение из `run.conditions`. Расстояние в сантиметрах подтверждает только положительное конечное число. `build_id` должен однозначно определять фактическую сборку. Чистая сборка может использовать Git SHA, а локально изменённая требует отдельного идентификатора, например SHA-256 APK. В варианте сборки указывают тот же `build_id`. Для JSON-профиля `git_sha` сопоставляется с этим идентификатором, `model_sha256` с моделью, остальные ключи с `operator.settings`.

Строки отчёта содержат A, B и `delta` по каждому показателю. Для числа срывов `delta.value` равно B − A. Для категорий, кругов и логических исходов результат `same` или `changed`. Незавершённый прогон, конфликт завершённости попытки и эталона, неподтверждённые или разные условия и неизвестный ответ оставляют исходы видимыми и дают `delta.reasons`. Сохранённые записи с неподдерживаемой или различающейся версией блокируют сравнение с указанием причины. `conditions.state` описывает совпадение условий. `result_state` отдельно показывает полноту расчёта разностей и принимает значения `insufficient_data`, `partial` или `complete`. Статусы Android-журнала и синхронизации в расчёте не участвуют. Массив записей хранит исходные ответы. Отчёт сравнения пересчитывается по выбранной паре.


## Форма, хранение и перенос

Перед запуском раскройте «Фактические условия перед запуском», введите подтверждённые сведения и отклонения, затем поставьте отметку подтверждения. Стенд сохраняет этот снимок в `attempt.manual_setup` с `provenance: 'operator'`. Пустые поля остаются неподтверждёнными. Подтвердите условия для следующего варианта или выбранного повтора. Подтверждение относится к конкретной серии, паре, варианту и номеру попытки. При смене цели или правке условий отметка сбрасывается. Для запуска с подтверждёнными условиями поставьте её заново. Перед следующим вариантом и повтором стенд сверяет цель с очередью в транзакции резервирования. Номера попытки и фактического порядка берутся из сохранённой серии. Если очередь изменилась, стенд показывает актуальную цель и ждёт нового запуска. Неудачное резервирование номера не расходует.

После запуска выберите нужную попытку в строке пары и нажмите «Ручная оценка A» или «Ручная оценка B». В форме можно уточнить фактические условия, ввести частичные ответы и сохранить оценку. Повтор с новым `run_id` открывается с пустыми ответами. Редактор сохраняет привязку к открытым `series_id` и `run_id`, даже если пара или серия изменится до окончания записи.

`series.manual_observations` содержит исходные записи `MotionManual.save`. Источник записей указан в `series.metadata_provenance.manual_observations`. Тот же снимок A/B проходит через общую очередь и IndexedDB. При изменении поля форма сразу показывает, что есть несохранённые изменения. «Сохранено» относится к отправленным ответам и появляется после подтверждения транзакции. Перед выгрузкой серии стенд перечисляет несохранённые версии, включая формы, скрытые после смены попытки. Кнопка у каждой оценки открывает нужный черновик без изменения выбора A/B. После сбоя записи или конфликта отправленная версия остаётся доступна для выгрузки из памяти до закрытия страницы.

Ручной JSON формата `dronecv-motion-manual-bundle-1` содержит версию правил, комплект A/B с эталонами, условиями, попытками, выбором пары и исходными записями, а также результаты по выбранным парам с причинами ограничений. Импорт проверяет контрольные суммы, привязки и воспроизводимость результатов. Эталоны и серия записываются одной транзакцией поверх актуального состояния IndexedDB. Оценка также записывается поверх актуальной серии после сверки попытки и исходной записи. Изменения других вкладок сохраняются. Конфликт ID или правок одной оценки прерывает запись с объяснением. После успешной транзакции вкладка принимает записанное состояние и сохраняет свои ещё не отправленные изменения. Прежний A/B JSON без ручных записей открывается с пустыми оценками. Импорт обновляет данные на открытой странице и сохраняет черновики в памяти. Импортированные эталоны сразу входят в «Экспорт серии JSON» и учитываются в лимитах 20 прогонов и 120 000 отсчётов. История сохраняет прогоны, доступные только в памяти. «Повторить» использует план последнего локального запуска. Журнал Android и совместимая синхронизация для переноса ручных оценок не требуются.

CSV содержит строки показателей по попыткам, включая состояние ответа, значение, причину, примечание, признак выбора и источник. `operator` обозначает ответ оператора. `scenario` обозначает вывод по фазе, `protocol` обозначает другие автоматически выведенные отметки по правилам протокола. У ответа, который не заполнен, источник пустой. Производные источники хранятся в `answer_sources`. Для восстановления серии используется JSON.
