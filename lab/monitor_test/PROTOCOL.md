# Протокол испытания «телефон → экран» (этап 6.6)

Для оператора стенда на MacBook или внешнем мониторе. Основная инструкция «Как пользоваться?» находится непосредственно в галерее. Этот протокол задаёт методику, единицы, источники данных и ограничения. Стенд исследует долю правильных обнаружений YOLO11s по ширине объекта в **кадре анализа смартфона**, сохраняет график/испытанную границу и использует её для сравнения фотографий. Он не восстанавливает исходную дальность до неизвестного дрона по фотографии.

## 1. Установка

- Откройте скачанный `gallery.html` вместе с `experiment.js`, `manifest.js` и `images/` по [README](README.md#как-скачать-и-запустить). Просмотр файла на GitHub не запускает галерею.
- Перенесите окно на нужный дисплей, задайте масштаб браузера (для повторяемости 100 %: Cmd+0 / Ctrl+0), включите полный экран **F**. Делайте это **до калибровки физического экрана**. Диагональ MacBook 13″ и разрешение внешнего монитора не используются как доказанный физический масштаб.
- Зафиксируйте яркость экрана, освещение, фон, отсутствие бликов и настройки камеры. Сохраните в заметке/журнале телефон, версию APK и модели YOLO, ориентацию, зум, физический ID камеры, фокус/экспозицию и фактические размеры кадра анализа W×H из приложения.
- Телефон установите на штатив. Ось камеры — приблизительно перпендикулярно экрану, коптер — вблизи центра экрана и кадра. Измерьте расстояние **от объектива используемой камеры до плоскости экрана**, введите см с допустимой дробной частью. Пустое поле — `null`: угол и дальность тогда не рассчитываются.
- Заранее установите и запишите порог confidence в приложении; для приведённой ниже серии — **50 %**. Введите те же 50 % в расширенных настройках галереи. Это только запись условий: поле галереи не управляет приложением и первоначально может содержать другое значение. Не меняйте порог внутри серии.

## 2. Выборка и прогоны

**Выборка** хранит фиксированные ID изображений и их порядок. «Пилот — 20 фото» даёт 5/5/3/3/2/2 снимка по категориям, seed 66020, код `S0d95e824`. Доступны полный набор, количества по категориям с seed и кнопка **«Выборка: только этот снимок»** для выбранного изображения эталона.

**Прогон** фиксирует телефон, зум, расстояние, масштаб, калибровку, границы и параметры эталона. В «Галерея и сравнение» разрешено подтвердить границы текущего объекта и изменить предположение о его ширине без потери уже записанных ответов: новые записи используют обновлённые параметры, прежние сохраняют свои снимки. В исследовании параметры эталона/установки фиксируются; при смене телефона, 1×/5×, расстояния, кадра анализа или новом замере экрана начинайте новый прогон. В `runs[].trial` сохраняются позиция и параметры каждого прогона; кнопки продолжения галереи/исследования восстанавливают соответствующий режим.

В расширенном режиме задаются уровни N и **1–100 попыток на снимок и уровень**. Порядок: уровень → изображение → попытки. Переход **→** открывает следующую попытку. Повторное **R** на прежней позиции заменяет запись, а не добавляет повтор. Для сравнения 1× и 5× оставляйте ту же выборку и уровни; новую выборку создавайте для новой серии. «Измерить предел» использует готовый план из 20 проверок на уровень и сохраняет исходное состояние галереи; переключение разделов не удаляет ответы.

## 3. Быстрый тест (по умолчанию)

Этот режим сохраняет прежний обзорный сценарий: фотография вписывается в окно, объект центрируется, один показ на изображение. Физическая калибровка и эталон не требуются.

1. Выберите «Пилот — 20 фото», задайте телефон, зум и измеренное расстояние, нажмите «Начать прогон».
2. После стабилизации приложения нажмите **R** и выберите: **1** — рамка на показанном объекте; **2** — рамка только в другом месте; **3** — рамок нет. Выбор в быстром режиме сохраняется сразу.
3. До выбора 1/2 можно ввести максимальный confidence, 0–100 %, включая дробные значения. Пустое поле и вариант 3 дают `null`.
4. **A** открывает категорию и итог только после записи; **→** — следующий снимок; **S** — настройки и экспорт. Повторите тот же список с другим зумом новым прогоном.

Для дронов (`civil_quadcopter`, `military_uav`, `uav_payload`) 1 означает TP, 2/3 — FN. Для птиц, самолётов и пустого фона любая рамка — FP, отсутствие рамок — TN. `false_alarm` дополнительно учитывает ошибочные рамки вне объекта. Неизмеренные размеры остаются `null`. Быстрый режим может использовать сохранённые подтверждённые границы, физическую калибровку и проверенный k для автоматической геометрии; CSS px не заменяют размеры кадра камеры. Порог хранится как условие прогона и не управляет приложением.

## 4. Расширенный режим

### Калибровка физического экрана линейкой

1. На основном экране нажмите **«Калибровка экрана»**. Контрольная SVG-линия и две высокие вертикальные риски расположены перед текстом, с отступами внутри видимой области. При узком окне длина линии адаптируется; фактическая длина в CSS px подписана под ней.
2. Измерьте обычной линейкой расстояние **между рисками**, введите **см** и сохраните. Это единственное обязательное число калибровки; название дисплея находится в «Дополнительно».
3. Коэффициент `cm_per_css_px = введённая_длина_см / line_css_px`. В данных он хранится как `mm_per_css_px = cm_per_css_px × 10`. Физическая мера определяется линейкой, а не CSS-дюймами, DPR, диагональю MacBook или разрешением монитора. Закройте панель C / Esc; коэффициент и статус видны на основном экране.
4. После **нового** замера начните новый физический прогон. Старый прогон не принимает другую калибровку незаметно. Для контроля можно один раз измерить ещё один отображённый размер.

После повторного открытия/импорта калибровка сохранена, но не активируется без подтверждения. Если геометрия браузера совпадает и **оператор удостоверился, что физический дисплей и масштаб те же**, доступна кнопка **«Экран и масштаб те же — подтвердить»**. Она позволяет продолжить прежнюю установку без повторного ввода длины. При изменившейся геометрии нужен новый замер линейкой и новый физический прогон.

Изменение DPR, размеров/положения окна, доступных размеров экрана или visual viewport делает коэффициент неактуальным. Браузер не гарантирует распознавание двух разных физических экранов с одинаковой геометрией. После переноса на другой дисплей, смены fullscreen/масштаба браузера/ОС и при сомнениях используйте **«Дисплей или масштаб изменён»** в «Дополнительно» и повторите измерение. При переходе с MacBook на 4K-монитор исходный код менять не нужно.

В режиме `physical` неактуальная калибровка блокирует продолжение и сохранение даже с ручными мм. В остальных режимах ручной контрольный замер допустим без физической калибровки и остаётся помеченным как ручной.

### Границы объекта и эталон

**Встроенный профиль — Draganfly Flex FPV 10:** пропеллеры 10″, собранный аппарат **570 × 570 × 60 мм**, номинальная ширина **57 см** для соответствующей проекции. Источники — [сайт производителя](https://draganfly.com/flex-fpv-system/) и [официальная брошюра февраля 2026, стр. 11](https://draganfly.com/wp-content/uploads/2026/02/DPRO-Product-Brochure-Feb-2026.pdf#page=11). Диаметр пропеллеров не подменяет полный габарит. Пользовательский профиль, ширина, источник и статусы доступны в «Дополнительно».

Готового распространяемого эталонного фото с подтверждённой проекцией 57 см в поставке **нет**. Найденные официальные фотографии перспективные: [изображение 2026/01](https://draganfly.com/wp-content/uploads/2026/01/Flex-10-Inch-2026-Photoroom.webp), [изображение 2026/08](https://draganfly.com/wp-content/uploads/2026/08/Flex-10-Inch-19.webp). Для них не установлены требуемая проекция полного габарита и разрешение на включение/изменение в этой поставке; изображения не встроены в стенд. Подтверждённые характеристики не означают автоматически допустимую и геометрически подходящую фотографию.

В разделе **«Измерить предел»** загрузите собственный снимок или изображение с разрешением на использование: PNG/JPEG/WebP до 20 МБ, каждая сторона не более 16 000 px. Для хранения создаётся JPEG-копия с большей стороной до 2048 px; слишком большая подготовленная копия отклоняется. Она сохраняется в браузере и JSON. Подтвердите модель и соответствие **видимой горизонтальной ширины** снимка габариту эталона. Для перспективного/повёрнутого ракурса нельзя без обоснования приравнивать его видимую ширину к 57 см; выберите подходящий ракурс либо собственную обоснованную геометрическую модель/ширину.

Нажмите **«Выделить границы эталона»**. В обычной галерее доступна кнопка **«Границы текущего объекта»**. Обведите именно коптер мышью или задайте `x₁,y₁,x₂,y₂`, затем подтвердите. Координаты относятся к сохранённой фотографии, для загруженного снимка — к подготовленной копии. Не обводите пустые поля или всю фотографию вместо коптера. Приблизительный `object_bbox` манифеста — лишь предложение, не подтверждённое измерение. Автоматические физические мм требуют подтверждения оператора.

Сохраняются bbox, размеры изображения, SHA-256 и дата. После повторного открытия выделять тот же объект заново не требуется. Ширина — **горизонтальная ширина bbox между точками A–B**, а не большая сторона. Реальный габарит должен соответствовать этим же точкам. Подтверждение рамки не является проверенной IoU-разметкой и не доказывает правильность YOLO автоматически.

Для неизвестных моделей обычной галереи действует явное предположение **«считаем коптер шириной 57 см»** (`reference_status=assumed`), редактируемое в «Дополнительно». Оно даёт условную эквивалентную дальность, а не реальный размер неизвестного аппарата. `conditional` означает отладочный эталон; `verified` — модель, проекция и источник подтверждены **оператором**, не программой. Изменение эталона в записи отражается как `manual_unverified`; прежние записи могут иметь `legacy_manual`.

### Калибровка камеры (C)

Это **другая калибровка**: `k` задаёт px кадра анализа камеры на один px монитора и не заменяет мм/CSS px.

1. При установленном телефоне и выбранном зуме нажмите **C**: отображаются квадраты 512, 256, 128, 64, 32, 16 px монитора с учётом DPR.
2. Сделайте скриншот приложения. Измерьте сторону квадрата 256 px (`a`, px скриншота) и ширину отображённого превью (`P`, px скриншота).
3. Если превью отображает тот же upright crop целиком по ширине, размер стороны в кадре анализа `s = a / P × W`, где `W` — **фактическая** ширина этого crop из приложения. При обрезке/полях используйте реальное преобразование crop → preview, не ширину всего скриншота. Если оно неизвестно, оставьте измерение пустым.
4. Введите `s`: галерея вычислит `k = s / 256`. Проверьте другим квадратом, например 64 px должно дать около `64 × k` px кадра.

После проверки по второму квадрату отметьте **«Калибровка камеры проверена по второму квадрату»**. Сохраняется контекст: телефон, зум, расстояние, W×H кадра, k, калибровка экрана и DPR. Само наличие числа k в техническом поле не подтверждает независимый размер для графика предела. Повторяйте проверку после смены телефона, камеры/зума, расстояния, ориентации, crop/размера анализа или установки экрана. Флажок — заявление оператора о выполненном замере, а не автоматическая метрологическая проверка.

### Режимы масштаба

| Режим | Значение уровня N | Условия |
|---|---|---|
| `physical` | горизонтальная ширина коптера в **см экрана**, например `6,4,3,2,1` | актуальный замер мм/CSS px, подтверждённые границы, центрирование; объект должен помещаться целиком |
| `camera` | **большая сторона** объекта в px кадра анализа, например `64,32,16,8` | измеренный k |
| `monitor` | большая сторона объекта в px монитора | физический масштаб и k не обязательны |
| `native` / `fit` | фиксированный коэффициент / вписать фотографию | обзор; физический размер доступен при подтверждённых границах и актуальной калибровке экрана |

Пустые фоны вписываются в окно; в режимах с N они повторяются в соответствующих контрольных блоках, но размера объекта у них нет. Масштабирование сохраняет пропорции фотографии. Автоматическая физическая ширина берётся из границ объекта, а не из ширины фотографии; при обрезке объекта экраном расчёт недоступен.

### Дополнительные поля записи

Обычная запись — **R → 1/2/3**. В исследовании с закрытым «Дополнительно» выбор сохраняется сразу; при открытых дополнительных полях выберите исход, заполните измерения и нажмите «Сохранить» / Enter. Пустые измерения — `null`, размеры положительные. Предварительно скрывайте G/I и формы, чтобы служебный текст не попадал в сцену. Повторное R исправляет прежнюю запись; для новой проверки нужна следующая позиция.

- `max_confidence_pct`: максимум за фиксированное окно наблюдения. Для 1 — рамка на объекте, для 2 — ошибочная рамка в другом месте; для 3 — `null`. `target_conf_pct` позволяет отдельно записать confidence на объекте, `fp_count` / `fp_max_conf_pct` — ложные рамки вне объекта.
- **Ширина и высота в кадре анализа**: ручной замер самого видимого объекта, с источником `manual_screenshot`, `manual_diagnostic` или `manual_other` (описать в заметке). Это не ширина фотографии, браузерного элемента или всего скриншота. Укажите W×H кадра анализа; размер объекта не может превышать соответствующий размер кадра.
- Существующее поле большой стороны `object_camera_px_measured` сохранено. Если оно пустое, а введены обе стороны, большая сторона вычисляется как их максимум. По одной большой стороне ширина и высота не восстанавливаются.
- В физическом блоке показаны рассчитанные мм и дальность. **Контрольный ручной замер ширины на экране** в мм необязателен и имеет приоритет над расчётом; оба значения сохраняются. Ручной контроль не переносится на следующий показ. В галерее изменение параметров эталона понижает его статус до `manual_unverified`. В исследовании габарит/источник зафиксированы: для их изменения требуется новый прогон с пользовательским профилем.

Для графика предела используется `truth_camera_width_px`: ручная разметка **самого объекта** по скриншоту (`manual_object_annotation`) либо подтверждённая геометрия камеры (`verified_camera_calibration`). Одно число CSS px или неподтверждённый k независимую ширину не создают. При пропуске YOLO истинная ширина всё равно измеряется/вычисляется; она не становится нулём. Размер предсказанной рамки и истинный видимый размер могут различаться.

### Импорт Android для текущей проверки

До начала серии раздел **«Автоматически заполнить настройки из Android JSON»** позволяет перенести настройки без добавления результатов. Для привязки файла к проверке в форме R раскройте **«Импорт Android для текущей проверки»** и выберите диагностический JSON `schema_version=1` с массивом `frames`. Сигналы `target_signal` v1/v2 разбираются с проверкой доступных полей. Метаданные могут заполнить телефон, модель/SHA-256, порог confidence, NMS и фактический W×H анализа; неизвестное остаётся null. Зум/физический ID камеры из отсутствующих полей не угадываются.

В отчётах с LK наблюдения хранятся отдельно в `tracking`. Импорт учитывает `frames[].detection_count`: больше нуля означает кандидата YOLO, ноль — отсутствие кандидатов. В таких строках координаты, confidence рамки и размер кадра остаются неизвестными. Рамка LK не участвует в подсчёте кандидатов и оценке исхода. Такие метрики анализируйте по [формату сопровождения](../../docs/reference/data-model.md#наблюдения-lk).

Текущий `target_signal` содержит центр цели, размер upright crop и confidence, **но не bbox коптера**. Наличие `detected` означает кандидата детектора, а не доказанный TP. `candidate_frame_count` — число кадров с таким сигналом, не число правильных обнаружений. Соответствие рамки эталонному объекту и исход 1/2/3 подтверждаются вручную.

Ожидающий импорт принадлежит текущим `run_id` и `step`. Новый выбор файла, снятие импорта, закрытие формы и смена проверки отменяют прежний запрос. Его поздний результат или ошибка не меняют запись, метаданные устройства, подписи и поле выбора файла. Это действует и для импорта настроек устройства.

Файл должен относиться только к текущему статичному показу. **Один импортированный файл = одна подтверждаемая оператором проверка**, независимо от числа его кадров. Заранее выбран первый сохранённый кадр файла; исход по нему подтверждается оператором, а не выбирается лучший кадр задним числом. Нужен скриншот/кадр записи для подтверждения соответствия рамки: сам JSON содержит лишь центр. Сохраняются имя/SHA, метаданные, счётчики, исходные confidence кандидатов и до 32 сигналов; исходный полный файл храните отдельно. Эти confidence не подставляются как confidence правильного обнаружения автоматически. Повторный SHA в другой записи не превращает один файл в независимые проверки. В исследовании одна запись — один заранее выбранный и подтверждённый кадр (`observation_unit=frame`), поэтому `checked_frame_count=1`, а исходы кадра следуют из ручного ответа. Это не число всех кадров файла. В прежнем режиме окон наблюдения (`window`) покадровые счётчики остаются null. Старые наблюдения без подтверждённой единицы `frame` сохраняются, но не превращаются в покадровый предел. Импорт detected/no_target не подтверждает соответствие объекту автоматически; противоречащий известному сигналу ответ блокируется, импорт можно снять.

Если фактический телефон или W×H импорта не соответствуют калиброванной установке, камерные оценки не применяются незаметно. Импортируйте/уточните метаданные и откалибруйте подходящую установку. Ручной режим без Android JSON остаётся полноценным: оператор подтверждает исход и использует проверенный k либо независимую разметку объекта.

### Короткий эксперимент для 10-дюймового коптера: 1× и 5×

1. Откройте HTML на MacBook, настройте fullscreen и физический экран. На основном экране нужны два числа: длина линии в см и расстояние от камеры до экрана в см. Выберите **«Измерить предел»**; профиль Flex FPV 10 уже заполнен.
2. Загрузите допустимый собственный снимок, подтвердите модель/проекцию и один раз сохраните bbox. Не подтверждайте перспективный снимок как 57 см без геометрического обоснования. Без подходящего фото опыт именно с реальным Flex FPV 10 не готов, хотя формулы можно отлаживать на условном эталоне.
3. Зафиксируйте Xiaomi 17 Pro примерно перпендикулярно экрану, **1×**, физический ID камеры, реальный кадр W×H, версию APK/YOLO и SHA модели, confidence/NMS, яркость/свет/фон, фокус/экспозицию. Проверьте k по двум квадратам и подтвердите контекст. Дополнительные параметры находятся в «Дополнительно»; при наличии Android-метаданных не вводите их повторно без необходимости.
4. Организуйте **проверки заранее выбранных кадров после повторной стабилизации**, а не двадцать соседних кадров одного показа; подтвердите это флажком. Флажок фиксирует заявление оператора, но не доказывает независимость. План независимости и условия запишите в журнал; сильно коррелированные окна не дают требуемых 20 независимых испытаний.
5. Нажмите **«Начать исследование: 20 проверок на размер»**. Готовые уровни: **6,4,3,2,1,0.5 см** ширины на экране. Объект должен целиком помещаться в экран и кадр камеры. G скрывает подписи и кнопки управления; выключите также I, дождитесь стабилизации и зафиксируйте заранее выбранный кадр (например, через одинаковую задержку после повторной установки; используйте скриншот/запись экрана). TP — правильная рамка на объекте именно на этом кадре. Не выбирайте лучший кадр за окно наблюдения и не игнорируйте неудачные кадры. Для непрерывной устойчивости видеопотока нужна отдельная временная методика.
6. **R → 1/2/3**, при наличии — Android JSON текущей проверки и confidence. Истинная ширина камеры автоматически берётся из проверенной геометрии; при отсутствии такой геометрии измерьте сам объект по скриншоту в дополнительных полях. Пропуски записывайте обязательно. **→** — следующая проверка. Повторное R лишь исправляет ответ.
7. В **«Результаты»** выберите серию и ось X: px камеры или эквивалентные метры. График и таблица строятся из сохранённых записей, показывают n, TP/FN/FP и интервалы. До опыта график пуст. При неустановленном переходе кнопкой **«Добавить промежуточный размер»** добавьте ещё 20 проверок между уровнями с заметным изменением доли либо на меньшем уровне; это новая серия записей в текущем исследовании, не анимация движения.
8. Для **5×** оставьте телефон на измеренной отметке, проверьте реальную камеру/кадр и заново подтвердите k для этого контекста. Начните отдельное исследование; данные 1× не смешиваются с 5×. Негативы проверяйте отдельно с теми же условиями/окном; их FP не подменяют пропуски дрона.
9. Сохраните набор и экспортируйте JSON (для восстановления) и SVG графика/CSV (для отчёта). Перезапуск не требует заново собирать результаты: откройте «Результаты» или продолжите нужный прогон после проверки экрана/установки. На внешнем 4K-мониторе выполните новую физическую калибровку и камеру k, затем повторите методику.

### График и критерий предела

Новый исследовательский алгоритм фиксирован: **не ниже 90 % успешных проверок и не менее 20 независимых проверок на уровне**. Это не настраиваемый технический критерий старой `repeat_summary`. Учитываются и общая доля TP, и доля среди проверок, помеченных независимыми. Флажок не делает последовательные кадры независимыми физически.

Уровень включает **все** записанные исходы, в том числе FN без измеренной ширины. Если истинная независимая ширина отсутствует хотя бы у одной проверки уровня, его камерная координата не подтверждена: уровень остаётся в таблице/знаменателе, но не используется как подтверждённая точка порога по px. Он не исчезает из статистики ради улучшения recall. Сохраняются число неизвестных размеров и источники.

График X=px камеры использует медиану независимых истинных ширин полностью измеренного уровня; Y=TP/число проверок. Альтернативная ось — эквивалентная дальность по известным физическим размерам. Для негативов отдельно сохраняются FP/TN и доля ложных срабатываний. Confidence — медиана доступных правильных обнаружений, для негативов — ложных; отсутствующий confidence не заменяется нулём.

95%-интервалы Wilson показываются как **номинальные** интервалы доли. Их интерпретация требует независимости наблюдений; они не компенсируют корреляцию кадров или малое разнообразие сцен.

Алгоритм не экстраполирует:

- `empty` / `insufficient` — нет результата либо недостаточно проверок/независимых размеров.
- `all_pass` — все достаточно испытанные размеры устойчивы: нужно проверить меньшие, предел не установлен.
- `all_fail` — все не достигли критерия: нужны большие размеры, предел не установлен.
- `contradictory` — меньший объект устойчив, а больший нет: единственный порог не установлен, уровни нужно повторить.
- `bracketed` — среди достаточно испытанных размеров есть меньший неустойчивый и больший устойчивый, без инверсии. Выводятся минимальный испытанный устойчивый px, максимальная проверенная эквивалентная дальность, доля и n. Интервал между уровнями не измерен; незавершённые/недостаточные уровни сохраняют предупреждение о неопределённости.

### Повторное использование в галерее

В **«Галерея и сравнение»** продолжите прежний прогон или выберите 20/90/свой набор. Для текущего снимка один раз подтвердите bbox, затем меняйте масштаб кнопками или +/−/0. **G** показывает мм, эквивалентную дальность и сравнение с выбранной сохранённой серией.

Для неизвестного коптера значение 57 см — **явное предположение**. Автоматическая геометрия относится к видимой ширине объекта, а не к ширине всей фотографии. Сравнение камерных px возможно только по проверенной установке; если её нет, физическая дальность может быть доступна, а сравнение с порогом — нет.

Точное сравнение требует известных совпадающих телефона, 1×/5×, W×H анализа, имени и SHA-256 модели, confidence, NMS и физического ID камеры. Различающиеся/неизвестные условия дают ориентировочное сравнение или отсутствие результата. Размер ниже подтверждённого диапазона помечается; размер выше максимального испытанного диапазона также не экстраполируется. Попадание внутрь диапазона эталона **не гарантирует обнаружение** другой фотографии с иным фоном/контрастом/ракурсом.

## 5. Размеры и экспорт

### Расчёт ширины, угла и дальности

```text
mm_per_css_px = измеренная_длина_линии_мм / длина_линии_CSS_px
screen_width_mm_calculated = (bbox.x2 - bbox.x1) × CSS_scale × mm_per_css_px
screen_object_width_mm = ручной_замер_мм, иначе screen_width_mm_calculated
D_equiv_m = drone_width_cm × distance_cm / (screen_object_width_mm / 10) / 100
angular_width_deg = 2 × atan(screen_object_width_mm / (20 × distance_cm)) × 180 / π
```

`CSS_scale` — фактическое число CSS px на один px исходной фотографии. Автоматический расчёт требует одновременно актуальной калибровки экрана, подтверждённой рамки и полного отображения объекта. Ручной замер ширины может дать физическое значение без автоматической калибровки. Ни приблизительный bbox, ни прежнее `object_monitor_mm` не подставляются в формулу дальности. Нет положительного обязательного измерения — `null`, а не ноль. Для негативных категорий эквивалентная дальность не рассчитывается.

**Пример геометрии:** номинальная ширина Flex FPV 10 57 см, расстояние 150 см, ширина на экране 3 см (30 мм) → **28,5 м**. Числа установки — пример формулы, не выполненный физический опыт. Для неизвестной модели те же 57 см остаются предположением. Прежний условный тест 60 см / 150 см / 3 см даёт 30 м. Зум отдельно на 5 не умножается: его влияние проверяется через наблюдаемые размеры и детекцию.

Формула сопоставляет угловой размер одной и той же ширины A–B у центрированного изображения и эталона. Для плоского фронтального объекта отношение ширин следует из геометрии; применимость к реальному объёмному коптеру приближённая из-за ракурса, перспективы, определения габарита и погрешности измерений. Доказательства реальной дальности в полёте из этой формулы не следует.

### Формат JSON и совместимость

Формат остаётся **`dronecv66-session-2`**, ключи браузера — `dronecv66v2.*`. Корень: `format`, `exported`, manifest metadata, `sample`, `runs`, `trial`, `settings`, `results`, `size_summary`, `repeat_summary`, `screen_calibration`, `object_bounds`, `experiments`, `local_images`, `reference_image`, `device_profile`, `camera_calibration`, `gallery_state`. Подготовленные **свои** снимки включаются в `local_images` как локальные data URL; 90 изображений исходного набора по-прежнему не включаются.

- `screen_calibration`: `id`, `created`, `label`, `line_css_px`, `line_mm`, `mm_per_css_px`, `environment`. Последний хранит DPR, доступные размеры экрана, viewport, положение окна и visual scale для проверки актуальности.
- Корневой `object_bounds` хранит подтверждения по ID изображения: `bbox`, `image_width`, `image_height`, `image_sha256`, `confirmed_at`. Изменение исходного изображения/размеров/SHA делает неподходящее подтверждение неприменимым.
- `trial.settings` содержит снимки калибровки, границ, `reference` (профиль/изображение, модель, размеры, источник, статус), контекст камеры и независимости, число повторов и критерий вместе с прежними настройками. `trial.order` хранит `{id, level, attempt}`. `runs[].trial` сохраняет позицию каждого режима; в результатах остаются использованные параметры на момент записи.
- `device_profile` содержит доступные метаданные Android; `camera_calibration` — контекст проверки k и дату подтверждения; `reference_image` указывает сохранённый снимок, а `local_images` — его подготовленную копию и подтверждение проекции.
- `experiments` — производный кэш графиков SVG, условий, точек и оценки предела, построенный из `results`. После записи/импорта/открытия он пересчитывается. Готовый порог или картинка без исходных проверок не становятся доказательством опыта.
- Импорт восстанавливает известную выборку/текущий прогон, добавляет отсутствующие прогоны по `run_id` и результаты по `(run_id, step)` с подтверждением. Существующие результаты не перезаписываются. Новые подтверждения границ добавляются только для подходящих файлов и отсутствующих ID. Корневые настройки автоматически не применяются: проверьте форму перед новым прогоном.
- Прежние файлы без новых полей импортируются: отсутствующие измерения остаются неизвестными (null либо отсутствующее новое поле), попытка — 1, старые ручные измерения сохраняются с пометкой источника. Старая версия результатов `dronecv66.results` доступна отдельной кнопкой экспорта, если такие данные есть в браузере.
- Импортированная/загруженная калибровка не подтверждает текущий физический экран автоматически. При совпавшей геометрии и подтверждённой оператором прежней установке допускается явное повторное подтверждение без ввода длины. После нового замера нужен **новый физический прогон**. Исторические измерения не пересчитываются по новой линейке. Угол/дальность вычисляются из сохранённых величин; все сводки и исследовательский кэш строятся заново, не принимаются на веру из импорта.

В «Результатах» доступны полный CSV/JSON, JSON выбранного набора и SVG текущего графика. JSON выбранного исследования сохраняет относящиеся к нему записи и нужные параметры/изображения. Хранение браузера может закончиться: при сообщении об ошибке экспортируйте резервную копию и освободите место. Импорт проверяет совместимость, но не является полной схемной валидацией произвольного JSON. Используйте собственные экспорты и сохраняйте их вместе с исходными Android JSON, фото установки и журналом версий/условий.

### Сводки результатов

Исследовательские графики/предел находятся в `experiments` и описаны [выше](#график-и-критерий-предела). Следующие две сводки сохранены для прежних сценариев и дополнительного анализа; их настраиваемый критерий не заменяет правило исследования 90 % / 20 независимых проверок.

**`size_summary`** сохраняет прежнюю сводку по большей стороне объекта в кадре анализа: один прогон, тип `drone`/`negative`, источник px и размер с округлением 0,1 px. Ручной замер имеет приоритет перед оценкой k; без данных — `unknown`. У пустого фона `control_level` в режиме camera означает только номер контрольного блока N, не размер объекта. Показываются проверки, TP/доля, отдельно FP/доля негативов, min/max эквивалентной дальности и число известных значений. `distance_reference_statuses` перечисляет статусы эталонов для известных дальностей; они также показаны рядом с диапазоном, чтобы условный габарит не выдавался за подтверждённый. Размеры 15,9 и 16,1 px остаются разными группами.

**`repeat_summary`** — сравнение повторных попыток одного изображения в одном прогоне при одинаковых записанных условиях: уровень, масштаб, зум/расстояние/порог, кадр анализа, физическая ширина, калибровка, границы, эталон и критерий. Изменение условий создаёт отдельную группу; разные прогоны автоматически не объединяются. Измеренный размер камеры может меняться между попытками и не разбивает группу.

Для повторов сохраняются `checks`, `correct_detections`, `detection_rate`, `false_positives`, `false_positive_rate`, `confidence_median_pct` и `confidence_known_count`; медианы ручных ширины/высоты камеры с количеством замеров, отдельно медиана ожидаемой ширины по k; ширина экрана, эквивалентная дальность, статус эталона и `stability_met`. Для дронов confidence берётся только из известных правильных обнаружений (сначала `target_conf_pct`, иначе `max_confidence_pct`), для негативов — из ложных срабатываний. Пропускам не приписывается confidence 0.

В прежней `repeat_summary` поле `stability_met` — true/false только после записанного технического минимума попыток и при известном критерии; иначе null. Оно не подтверждает исследовательский предел без проверки независимости/размеров и фиксированных 90 % / 20. Доля окон наблюдения не является долей кадров или полевой дальностью.

## 6. Интерпретация и оговорки

- Экран добавляет муар, ограничения яркости/контраста, отражения и частоту обновления; камера снимает плоскость. Перенос результата на реальный коптер в небе требует отдельного полевого испытания.
- Физические мм экрана, px монитора, px кадра анализа и px входа YOLO — разные величины. Без измеренного k или ручного замера нельзя подставлять браузерные px как размер объекта в камере.
- Ракурс, точность границ, линейки, расстояния, crop/preview и смена физической камеры влияют на результат. Проверяйте объект целиком в кадре; сравнивайте режимы только при зафиксированных условиях.
- Условный эталон нужен для отладки. Предположение о 57 см у неизвестной модели даёт только соответствие угловому размеру, не её исходную дальность. Подтверждённые характеристики Flex FPV 10 не подтверждают проекцию случайного фото и не снимают необходимость прав на его использование.
- Ручные испытания на MacBook/мониторе и Xiaomi 17 Pro должны подтвердить физические размеры, актуальность калибровки, геометрию камеры и реальные TP/FP/confidence. Автоматические проверки с синтетическими вводами этого не доказывают.

## 7. Движущаяся цель

Этот раздел описывает автономный сайт для записи одного сценария и анализа журнала телефона. Android-приложение и его параметры YOLO/LK не меняются. Новый эталон не назначает режим телефона: `mode: null`; фактический `yolo` или `yolo_lk` берётся из журнала. Прежние A/B-эталоны читаются с сохранёнными режимами и метаданными.

### Запуск и рабочая область

Выберите фото, один раз подтвердите границы дрона и нажмите «Старт». Ширина цели относится к подтверждённой рамке, а не к полям изображения. Фото масштабируется пропорционально и целиком помещается на маршруте. Начальные параметры: 40 px, 300 px/с, 500 px/с², один круг. Это настройки первого опыта, не измеренные характеристики сопровождения. Если фото с широкими полями не помещается, уменьшите ширину цели или увеличьте рабочую область. Условия телефона, зум и расстояние необязательны.

В «Рабочая область и метки для 5×» задаются положение и размер внутренней области в процентах полноэкранного canvas, сторона угловой метки и сторона ячейки sync-кода в пикселях canvas. Начальная область занимает 90 % ширины и высоты с отступами по 5 %; метка имеет сторону 48 px, ячейка sync-кода нового профиля 18 px. Сохранённые 6 px восстанавливаются без замены. Изменение области перемещает метки и ограничивает весь маршрут фотографии. Перед запуском проверяется, что маршрут, четыре метки, единственный sync-код с чёрной подложкой и отступы помещаются одновременно. Геометрия во время прогона фиксирована.

В этом разделе пиксели экрана означают координаты canvas: размеры полного экрана в CSS px умножаются на DPR и округляются. Это не пиксели камеры и не физические миллиметры. Предпросмотр области до запуска не содержит действующего sync-кода. До импорта телефона статус «Камерой не проверено» не позволяет сделать вывод о читаемости на 5×.

`MotionScenario.plan` резервирует место под внешний sync-код и вызывает `Motion.planMotion(input, {reserveMarker: false})`: дополнительная полоса под старый внутренний маркер не нужна. Вызов без второго аргумента сохраняет прежние маркер и геометрию `Motion.planMotion`. Ранее записанные эталоны читаются по сохранённым координатам шагов без перепланирования. Размер цели, угловых меток и ячейки задаётся в px canvas; DPR меняет доступный canvas и пересчёт CSS-прямоугольника кнопки, но не подменяет эти параметры. Контрольный сценарий первого запуска и размеры экрана указаны в [README](README.md#движущаяся-цель).

### Сценарий и повторение

`simple-motion-v1` использует фиксированный порядок:

| Фаза | Длительность и поведение |
|---|---|
| `calibration` | 2000 мс без фотографии; четыре угловые метки и sync-код уже видимы. |
| `stationary` | 1500 мс с неподвижной фотографией в начале маршрута. |
| Движение | Прямоугольный маршрут по часовой стрелке с разгоном, возможным равномерным ходом, торможением и остановками на поворотах; заданное число кругов. Длительность не менее 7000 мс. |
| `disappearance` внутри движения | Через 35 % времени движения фотография скрывается на 1000 мс. Положение продолжает рассчитываться по тому же маршруту (`hidden_motion: continue`); код и четыре метки остаются. До конца движения после возвращения остаётся не менее 3550 мс. |
| `blank_after` | 1500 мс без фотографии, с метками и кодом. Затем действующий код удаляется. |

Маршрут начинается в верхнем левом углу доступной области и проходит верхний правый, нижний правый, нижний левый и снова верхний левый. Ядро `motion.js` задаёт разгон и торможение на каждой стороне и базовую остановку 150 мс на повороте. Если базовый маршрут короче 7000 мс, его часы равномерно замедляются: `route_time_scale` меньше единицы; фактические скорости умножаются на этот коэффициент, ускорения на его квадрат. Заданные скорость и ускорение при этом остаются верхними ограничениями. Подробные длительности сохраняются в `scenario`. Допустимы 1–20 кругов и общая длительность до 120 с.

Положение вычисляется по прошедшему монотонному времени. `samples[]` содержит только фактически выполненные обновления canvas с положением, видимостью и векторами скорости/ускорения. Эти обновления не подтверждают физическую засветку пикселей монитора. С первого валидного кода `elapsed_ms` и `step_id` идут по одной шкале, включая калибровочную фазу; сброса времени после неё нет.

«Повторить» использует сохранённые фото, границы, параметры, рабочую область, метки и условия последнего начатого сценария, создавая новый `run_id` и собственные фактические шаги. Изменённые поля формы этот снимок не заменяют. Повтор отклоняется при несовместимости сохранённых размеров, DPR или доступных браузеру свойств экрана; для новой геометрии нужен «Старт». Браузер не предоставляет надёжную физическую идентичность одинаковых мониторов: после переноса установки оператор должен начать новую конфигурацию и заново проверить калибровку.

Естественный конец, «Стоп», Esc, выход из полного экрана, скрытие страницы, изменение геометрии и ошибки идут через общий путь завершения: анимация отменяется, незавершённый старт инвалидируется, действующий код и canvas удаляются, открываются настройки без прежней сцены галереи. Запись хранит `complete` и причину прерывания. До старта и после завершения действующего кода этого запуска нет.

### Сохранение и подбор эталона

Выбранный ID фото, параметры, рабочая область и размеры меток хранятся в `motion_settings` существующего localStorage галереи. Данные загруженного изображения, его идентичность и подтверждённые границы используют общее хранилище фотографий; разметка другого изображения не переносится. Снимок повторения сохраняет данные фотографии, а не временный `blob:` URL.

IndexedDB `dronecv-motion` разделяет запись текущего прогона и импорт готового файла. Перед показом первого действующего кода создаётся неполная локальная запись; шаги добавляются порциями по 120 обновлений и остатком при завершении. Полный статус записывается после сохранения шагов. При закрытии вкладки между порциями возможна потеря ещё не записанного хвоста, но такая запись остаётся неполной. Реальные прерванные прогоны сохраняются и доступны для экспорта. Ошибка транзакции или квоты показывается явно; эталон из памяти следует экспортировать до закрытия страницы.

Готовый файл сохраняется одной транзакцией по метаданным и всем шагам. До успешного commit импорт не появляется в подборе; отказ откатывает только эту транзакцию, не затрагивая прежние записи. Повторная попытка после отказа не создаёт ложного конфликта. Повторный импорт идентичного содержимого не добавляет копию; разные эталоны с одинаковым `run_id` сохраняют неоднозначность. Сравнивается содержимое эталона, а не порядок ключей JSON или служебная оболочка хранения.

История восстанавливается после перезагрузки. Служебные поля оболочки `source: local/import`, `local_sequence` и ключ `settings.lastLocalKey` отделены от эталона `run`. Локальный порядок выдаётся транзакционно при начале прогона; «Экспорт последнего запуска» использует указанный локальный запуск, включая Stop/Esc и другие прерывания, а не последний случайный ключ IndexedDB. Импорт прежнего файла не меняет этот указатель, локальный порядок и сохранённый сценарий «Повторить». Служебные поля не попадают в экспорт и не создают различий между одинаковыми эталонами.

Для прежних записей без надёжного порядка хронология не восстанавливается по случайным ID. Данные сохраняются без автоматического удаления; если последний локальный запуск установить нельзя, кнопка его экспорта недоступна и показана причина. «Экспорт серии» сохраняет доступ ко всем восстановленным записям. Новый локальный прогон создаёт надёжный указатель последнего запуска. В текущем наборе допускаются до 20 запусков, до 40 000 шагов на запуск и до 120 000 шагов суммарно. «Новая серия» начинает новый набор в памяти, сохраняя прежние записи в IndexedDB. JSON служит резервной копией и переносом; очистка данных браузера удаляет локальное хранилище.

Повреждённая запись `complete:true` без шагов, уже созданная прежним неатомарным импортом, автоматически не исправляется и может сохранять конфликт ID с правильным эталоном. Старое хранилище не позволяет надёжно установить её происхождение. Сначала сохраните экспорт серии, затем откройте стенд в отдельном чистом профиле браузера и загрузите исходный корректный эталон и журнал. Прежний профиль сохранит все записи. Новые отказы импорта полностью откатываются.

Загрузите журнал телефона. Импортёр читает `run_id` из экранных кодов, ищет сохранённый эталон и запускает калибровку и расчёт. Если эталона нет, загрузите его JSON отдельно. Несколько разных ID внутри журнала и конфликтующие эталоны с одним ID блокируют произвольный выбор. Одинаковые копии одного эталона не создают конфликта. Каждый новый импорт инвалидирует поздние результаты предыдущего чтения или декодирования кадра.

### Sync-код v1 и угловые метки

Каждое обновление canvas содержит ровно один sync-код с данными 10×8 ячеек и белым полем шириной в одну ячейку; общий размер 12×10 ячеек. Поле полностью окружено отдельной чёрной площадкой. `marker.x/y` указывает начало данных, `module_px` задаёт сторону ячейки. Чёрная ячейка означает 1, белая 0; чтение построчное, старший бит первым. Формат неизменён:

| Байты | Содержимое |
|---|---|
| 0 | `0xD1`, идентификатор формата. |
| 1–4 | `run_id`, unsigned 32-bit big-endian; в JSON восемь строчных hex-символов. |
| 5–8 | `step_id`, unsigned 32-bit big-endian; номер обновления с 0. |
| 9 | CRC-8 байтов 0–8: полином `0x07`, начальное значение 0, без отражения и финального XOR. |

Неизменённый Android-декодер ищет белое поле и проверяет сигнатуру, CRC и контраст. Кандидат меньше 24×20 px, шире или выше ¾ кадра, неоднозначность нескольких валидных кодов и изображение свыше 1 048 576 пикселей дают отсутствие кода. Это программные ограничения, а не гарантия чтения камерой. Четыре угловые метки не являются копиями sync-кода.

`dronecv-corner-8x8-v1` состоит из чёрной рамки 8×8 и внутреннего слова 6×6 из фиксированного набора `motion-calibration.js`. ID 0, 1, 2, 3 соответствуют TL, TR, BR, BL. Локальный JavaScript распознаёт эти метки по JPEG без CDN и внешних сервисов; новая Android-поддержка не требуется. Все четыре метки видимы с первого действующего кода, не перемещаются до завершения и не перекрываются фотографией.

### Автоматическая калибровка

Android сохраняет один калибровочный JPEG на первом кадре с успешно прочитанным sync-кодом. Сайт показывает именно этот кадр, обводит найденные метки, подписывает ID и сообщает пропуски или неоднозначность. Центры вычисляются проективно по найденным четырём углам метки, а не по середине её осевого bounding box. Проверяются уникальность ID, порядок TL→TR→BR→BL и невырожденность преобразования. После импорта нескольких журналов пригодные JPEG обрабатываются автоматически последовательно; переключать селектор для запуска распознавания не требуется. Калибровка хранится отдельно для каждого журнала; одинаковый размер изображения не переносит её между записями.

Селектор меняет кадр и фактический статус выбранного журнала: найденные ID, отсутствие JPEG, неоднозначность либо ручные точки. Позднее декодирование прежнего кадра не подменяет выбор. Готовность общего отчёта показана отдельно: метрики успешно обработанных журналов остаются видимыми, а ожидающие журналы перечислены с именами и причинами. Общий экспорт доступен после подготовки всех журналов; ошибка одного не объявляет калибровку остальных неуспешной. В экспорте `calibration_method` различает `automatic` и `manual`.

Стороны обнаруженных меток показываются в пикселях настоящего кадра. Размер ячейки sync-кода, полученный через гомографию, подписан как оценка. Успех «4 из 4 найдены» относится только к сохранённому JPEG; он не доказывает постоянную видимость меток и неподвижность телефона во всей записи.

При ошибке распознавания доступна «Ручная калибровка заново»: отметьте центры TL, TR, BR, BL на настоящем кадре. Для прежних эталонов ручная разметка остаётся способом сопоставления. Если JPEG отсутствует, ручной режим недоступен: измените размер или расположение sync-кода и повторите запись. Синтетическое изображение вместо кадра телефона не показывается.

### JSON эталона

Новые прогоны используют `dronecv-motion-run-2`; прежний `dronecv-motion-run-1` читается без изменения метаданных. Серия `dronecv-motion-series-1` объединяет записи в `runs[]`.

| Поле | Смысл |
|---|---|
| `run_id`, `series_id`, `mode` | ID прогона и набора; новый `mode: null` независим от Android. Прежние `pair_index`, `slot`, `order`, `mode` сохраняются. |
| `photo` | `id`, `sha256` при доступности, исходные `width`, `height`, `bbox`. |
| `conditions` | Необязательные сведения оператора и `viewport`: canvas/CSS-размеры, DPR, доступные свойства экрана. |
| `scenario` | `version: simple-motion-v1`, параметры движения, `workspace`, размеры меток, длительности фаз, `disappearance_start_ms`, `hidden_motion`, `route_time_scale`. |
| `calibration_points`, `calibration_markers` | Центры TL/TR/BR/BL и `{id,x,y,size}` каждой угловой метки в canvas. |
| `marker`, `sync_backing` | Начало данных, сторона ячейки и прямоугольник чёрной площадки `[x,y,width,height]`. |
| `duration_ms`, `complete`, `abort_reason` | Расчётная длительность, завершённость и причина прерывания; первоначально запись неполная. |
| `samples[]` | Реальные обновления: `run_id`, `step_id`, `elapsed_ms`, `phase`, `visible`, `bbox_screen_px`, `image_rect_px`, `velocity_px_s`, `acceleration_px_s2`. |

Время `elapsed_ms` отсчитывается от первого обновления, `step_id` начинается с 0. `phase` нового сценария: `calibration`, `stationary`, `accelerate`, `cruise`, `brake`, `turn`, `disappearance`, `blank_after`; старый сценарий также использует `blank_before`. Рамка и прямоугольник фото заданы как `[left,top,right,bottom]`, без фотографии равны null. Оси направлены вправо и вниз. Последний шаг может быть выполнен позже расчётного конца; расчётная траектория не подставляется вместо пропущенных обновлений.

### Журнал Android и синхронизация

Начните запись «Стенд движения» на телефоне до «Старта» сайта и остановите после заключительной фазы. Импорт принимает прежний JSON `dronecv-motion-android-1` и поток `dronecv-session-timeline-1` (`.ndjson`/`.jsonl`). Их Android-контракты не изменены; формат потока описан в [модели данных](../../docs/reference/data-model.md#поток-диагностической-сессии-dronecv-session-timeline-1). Ограничение загрузки 256 МиБ на файл. Исходные кадры с кодами, публикации и очистки нужны для оценки; отсутствие кадров или калибровки нельзя восполнить вымышленными значениями.

В прежнем JSON `frames[]` хранит `frame_id`, `analyzer_ns`, `capture_ns` и `marker: {run_id,step_id}` либо null; `publications[]` хранит момент публикации, источник и нормированную рамку либо null при очистке; `detections[]` содержит исходные детекции YOLO. `calibration_image` содержит размеры и JPEG. Координаты Android относятся к повернутому crop. Импорт NDJSON вычитает начало записи как `BigInt` до преобразования относительных времен в Number, сохраняет метаданные и проверяет целостность.

Интерфейс разделяет три независимых результата:

| Результат | Необходимые данные и область |
|---|---|
| Читаемость sync-кода | Только журнал: число кадров, считанных кодов и кадров без кода, все обнаруженные `run_id`. Доступна без эталона, JPEG и угловых меток, в том числе при нескольких ID или неполной записи. |
| Временное сопоставление | Журнал и однозначно найденный эталон: сопоставленные кадры, неизвестные шаги, чужие ID, отсутствие времени экспозиции, нарушения порядка сопоставленных кодов на кадрах с экспозицией, зависшие шаги, совместимый интервал смещения и его ширина. Пространственные точки не требуются; если эталон не выбран, указана причина. |
| Пространственная калибровка | Настоящий JPEG и четыре пригодных соответствия эталону. При отсутствии кадра или точек метрики точности недоступны, но два предыдущих результата сохраняются. |

Неполнота файла и незавершённость опыта показаны отдельно от доступных временных ограничений. Считанный код сам по себе не подтверждает временную синхронизацию. Часы браузера и камеры связываются одним постоянным смещением без масштабирования времени. Метки экспозиции ограничивают смещение полуоткрытыми интервалами фактических шагов; пересечение ограничений даёт совместимый интервал. Пустое пересечение означает несовместимость, отсутствие конечных границ означает недостаточную синхронизацию. Время анализатора не заменяет экспозицию, оптимальное по качеству рамок смещение не выбирается.

Время вне крайних кадров, разрывы более 250 мс, долгий шаг эталона и зависший код остаются неизвестными. При разных возможных исходах для совместимых смещений результат также неизвестен. Оболочки долей консервативны и могут быть шире точных экстремумов при одном фиксированном смещении. Читаемость sync-кода во всём журнале показывается отдельно от четырёх угловых меток в одном JPEG: сопоставленные, отсутствующие и чужие/неизвестные коды, нарушения порядка и статус синхронизации.

### Отчёт простого сценария

Новый экспорт `dronecv-motion-scenario-report-1` содержит `runs[]` с `criterion_version: motion-scenario-v4`. Он не применяет PASS/FAIL старого `motion-retention-v3` к новому знаменателю и не вычисляет A/B-максимумы.

Правильная рамка имеет IoU ≥ 0,5 между проецированным четырёхугольником эталона и действующей рамкой Android. Основной знаменатель T включает всё время видимой фотографии: неподвижность, движение и повороты. Исчезновение, калибровка без фото и конечная пустая фаза исключены. Отдельные `stationary` и `movement` показывают свои длительности и покрытие; в `movement` входят повороты. Подтверждённое правильное время G, неправильное B и неизвестное U дают T=G+B+U. Границы доли равны G/T и (G+U)/T; покрытие равно (G+B)/T. Самый длинный подтверждённый провал и возможный провал с неизвестными участками сохраняются отдельно.

`capture`, `cleanup`, `reacquisition` содержат `status`, `lower_ms`, `upper_ms`, `reason`:

- Первый захват отсчитывается от первого фактически показанного видимого шага до публикации правильной свежей рамки, до эпизода исчезновения.
- Очистка отсчитывается от первого фактически скрытого шага до снятия существовавшей перед исчезновением рамки; поиск продолжается после возвращения цели до конечной пустой фазы. Если отсутствие рамки перед исчезновением подтверждено, статус `not_applicable`; если предыдущее состояние неоднозначно, оценки нет.
- Повторный захват отсчитывается от первого фактически показанного шага после исчезновения. Нужно подтверждённое отсутствие координат во время или после скрытия и новая правильная публикация из кадра после возвращения. Пустое состояние действует до следующей публикации: очистка до скрытия подходит, если отсутствие координат продолжалось после начала исчезновения для всех допустимых смещений. Избыточный `clear` внутри того же пустого интервала результата не меняет. Старый `clear`, после которого рамка снова появилась до исчезновения, такого подтверждения не даёт. Неизвестное состояние не считается отсутствием. Сохранившаяся рамка даёт `no_confirmed_absence`, а не нулевой повторный захват; поздняя очистка после возвращения и последующий свежий захват остаются оцениваемыми.

`bounded` означает границы с учётом всех совместимых смещений; `right_censored` означает, что событие не подтверждено до конца доступного интервала, и сохраняет обоснованную нижнюю границу без вымышленного нуля. Для повторного захвата этот случай предполагает, что возвращение было показано. Если после исчезновения ни один фактический шаг не показал видимую цель, повторный захват имеет `unavailable` с причиной отсутствия зафиксированного возвращения. Неполная запись, незавершённый эталон и недостаточная синхронизация также дают `unavailable` со своими причинами. Конец наблюдения повторного захвата ограничен финальным исчезновением цели. Публикация состояния не подтверждает показ рамки на дисплее телефона; эти интервалы не являются p50/p95 текущей задержки координат.

`center_error` сохраняет расчёт по времени и происхождение `provenance`, описанные [ниже](#ошибка-центра-во-времени), но в новом сценарии его `domain` явно расширен до `all_visible_time_including_stationary_and_turns`.

### Прежние эталоны и критерий удержания

Для `dronecv-motion-run-1` остаётся `motion-retention-v3`, экспорт `dronecv-motion-report-4` и прежние метаданные. Область критерия включает только видимые `accelerate`, `cruise`, `brake`, без `turn` и пустых фаз. Для PASS требуются завершённые неусечённые записи, порядок меток, обе пустые граничные фазы, продвижение движения, покрытие не менее 90 %, нижняя граница правильного времени не менее 90 % и отсутствие возможного провала дольше 500 мс. Известный провал дольше 500 мс или верхняя граница ниже 90 % доказывают FAIL в валидной записи; в неоднозначных случаях результат null. Ровно 90 % и 500 мс допустимы. Старый диагностический захват измеряется от первого наблюдаемого видимого кадра до подходящей детекции YOLO и не подменяется новым `capture`.

Исторические `maxima[]` выбирают только испытанные уровни одной конфигурации, имеющие как минимум два разных `run_id` и только PASS по v3; FAIL, null или конфликт конфигураций блокируют уровень. Это не универсальный предел ускорения. Для пересчёта нужны исходный эталон и журнал с новой калибровкой; сохранённый отчёт не является входным журналом. Версии критериев не смешиваются.

### Аппаратная проверка на Xiaomi

Закрепите Xiaomi и монитор, выберите реальный режим 5× и впишите всю рабочую область в crop телефона. Запишите один полный прогон, экспортируйте журнал и сохраните резервную копию эталона. После импорта проверьте настоящий JPEG, четыре разных найденных ID, размеры меток в пикселях кадра и отдельно чтение sync-кода по всему журналу. Проверьте дополнительные точки внутри области и причины неизвестных интервалов отчёта. Повторите после изменения оптики, crop, зума или крепления. Синтетические тесты и программная совместимость декодера не гарантируют читаемость на 5× и физическую точность сопровождения.

### Ошибка центра во времени

Отчёт `dronecv-motion-report-4` добавляет `center_error` версии `motion-center-error-v1` и `provenance`. Критерий `motion-retention-v3`, IoU и PASS/FAIL сохраняются. Входные форматы v1 и NDJSON прежние; отчёты v3 остаются историческими результатами и не служат входом пересчёта. Чтобы получить новые поля, загрузите исходные записи и повторите калибровку. Определения и схема новых полей находятся в [модели данных](../../docs/reference/data-model.md#ошибка-центра-в-отчёте-движения-v4).

Ошибка измеряет расстояние между действующей опубликованной рамкой приложения и эталоном в тот же момент времени после согласования часов. Она учитывает отставание рамки от движущейся цели. Сравнение с положением цели в исходном кадре YOLO не входит в эту метрику. Момент публикации состояния контроллера не подтверждает момент отображения рамки на дисплее телефона.

Четыре угла экранной рамки переносятся существующей гомографией в нормированные координаты upright crop камеры. По минимумам и максимумам X/Y строится охватывающий прямоугольник; эталонный центр находится в его середине. Проекция исходного центра экранной рамки обычно даёт другую точку. IoU по-прежнему использует проецированный четырёхугольник.

Для рамки приложения `[l,t,r,b]` центр в пикселях камеры равен `[(l+r)/2*W, (t+b)/2*H]`. Эталонный центр переводится в пиксели теми же W и H; ошибка равна `hypot(app_x-reference_x, app_y-reference_y)`. Пиксели монитора, входа модели и камеры не взаимозаменяемы. Без размеров crop или при явном конфликте геометрии численная ошибка недоступна; непригодная калибровка останавливает расчёт с пояснением.

Временная область совпадает с областью удержания: только видимые `accelerate`, `cruise`, `brake`, каждый записанный шаг действует до следующего. Остановки и пустые фазы исключены. Изменения состояния действуют с момента публикации до следующего изменения; последняя публикация при одинаковом времени задаёт последующее состояние. Сохраняются правила `initial_snapshot`, очисток и неизвестности до первого состояния NDJSON. Для прежнего журнала v1 отсутствие публикаций означает отсутствие рамки.

Среднее, p50 и p95 взвешиваются длительностью, а не числом обновлений. Взвешенный квантиль q есть минимальная ошибка, для которой накопленная длительность ошибок не меньше q от оценённого времени. Максимум относится только к оценённым интервалам. Большие ошибки включаются независимо от IoU. Когда рамки нет, численной ошибки нет: такое время хранится отдельно от неизвестного. Частые повторные публикации одной рамки не меняют статистику.

Используется всё существующее множество допустимых общих постоянных смещений часов, без подбора по ошибке. Для каждого момента эталона рассматриваются все возможные состояния приложения. Численное значение учитывается только тогда, когда оно одинаково при всех смещениях; отсутствие рамки также должно быть однозначным. Остальное время неизвестно. Поэтому ненулевая ширина интервала смещения допускает полезное покрытие, например при неизменных центре и рамке. Статистики всей области при неизвестном времени или отсутствии рамки остаются `null`. Условные статистики и покрытие показаны рядом; они не оценивают неопределённую часть прогона.

Алгоритм сначала объединяет соседние интервалы одинакового состояния. Для интервала приложения `[a,b)` множество возможных моментов эталона покрывается `[a-hi,b-lo)`, где lo/hi ограничивают общее смещение. События начала/конца этих диапазонов разбивают каждый шаг эталона; sweep проверяет все активные значения, включая неизвестность вне наблюдений. Это покрывает внутренние смещения, а не только два конца. Состояние берётся из того же множества общих смещений; независимое удобное смещение для каждой рамки не выбирается. Границы меры ноль не влияют на длительности. Границы статистик не рассчитываются.

Для аппаратной приёмки отдельно запишите реальный прогон на Xiaomi: проверьте читаемость меток, пригодность экспозиций для единого смещения, соответствие W×H/rotation/crop и неизменность установки. После четырёхточечной калибровки проверьте дополнительные контрольные точки внутри области. Рассчитайте отчёт, проверьте покрытие и причины неизвестности; сохраните исходные записи и метаданные. Автоматические синтетические проверки подтверждают вычисления, физическая точность этим этапом не подтверждается.

### Длительная диагностическая запись

В отчёт движения можно загрузить прежний `dronecv-motion-android-1` или поток `dronecv-session-timeline-1` (`.ndjson`/`.jsonl`). При отсутствии завершающей строки, пропусках или прерывании опыта полный PASS недоступен. Сохранность записи, завершение сценария и наличие пригодного эталона проверяются отдельно; формат и поля описаны в [модели данных](../../docs/reference/data-model.md#поток-диагностической-сессии-dronecv-session-timeline-1). Ограничение браузерной загрузки — 256 МиБ на файл. Калибровочный кадр и читаемые метки движения по-прежнему обязательны для сравнения с эталоном.

Для физической приёмки запишите непрерывный прогон не менее 30 минут при достаточном свободном месте. Сохраните экспорт, проверьте завершающую строку, отсутствие пропусков и отчёт обоих анализаторов. Зафиксируйте размер файла, память процесса в начале и конце, частоту обновлений и задержки с записью и в сопоставимом прогоне без неё, модель телефона, сборку, настройки камеры и условия опыта. Не представляйте синтетическую нагрузку как испытание камеры или модели. Приёмка на устройстве требует отдельного фактического измерения.


## Проверка чтения sync-кода

Отдельная кнопка сайта запускает `dronecv-sync-check-1` без фотографии и разметки. Белый fullscreen содержит четыре прежние угловые ID-метки и ровно один sync-код. Его данные, порядок битов, CRC и восьмизначный hex `run_id` совместимы с установленным Android. Ячейка по умолчанию для нового профиля 18 px canvas, быстрые размеры 12/18/24/32, допустим ручной целый ввод. Сохранённые настройки сохраняются. Белое поле занимает одну ячейку: код вместе с ним 12m × 10m, внешняя чёрная подложка 14m × 12m. При m=18 это 216 × 180 и 252 × 216 px canvas. Размер в кадре камеры определяется съёмкой, а не этими числами.

Общая геометрия `MotionScenario.layout` проверяет размещение относительно четырёх углов и кнопки остановки. Маршрут дополнительно проверяет оставшееся место для фотографии. Нехватка места останавливает запуск с объяснением, без уменьшения кода. Крупное фото с широкими полями может не помещаться даже при целиком видимых метках; увеличьте область или уменьшите размер цели явно.

Каждая проверка получает свой `run_id`, не совпадающий с загруженной локальной историей движения и проверок. Шаг 0 показывается минимум 10 секунд; затем шаги 1–5 показываются минимум по секунде каждый. Время берётся из фактических RAF-вызовов отрисовки. При задержке браузера шаги удлиняются, не пропускаются. Неизменный код повторно не записывается. `steps[]` хранит только смены: `step_id`, `elapsed_ms` от первого показа, `browser_time_ms` монотонных часов браузера. `end_ms` фиксирует снятие сцены; `complete`/`abort_reason` отличают завершение и отмену. Эти моменты описывают работу браузера, а не измеренную физическую смену пикселей монитора.

Проверки хранятся в отдельном ключе `sync_reading_checks_v1` существующего localStorage-префикса стенда. Они не попадают в IndexedDB-эталоны, экспорт серии движения, последний запуск или «Повторить». Экспорт проверки — отдельный JSON с геометрией, viewport и шагами. Импорт этого JSON как эталона траектории отклоняется; отдельный импорт резервной проверки пока не реализован. После завершения, ошибки, отмены, скрытия страницы или изменения viewport canvas очищается и скрывается, включая фон под настройками.

Журнал загружается прежним импортом JSON/NDJSON, форматы Android не меняются. До анализа и назначения активного журнала проверяются массив `frames` и каждый его элемент: кадр должен быть объектом; необязательный `marker` допускает null либо объект со строковым `run_id` и uint32 `step_id`. Исторические строковые ID остаются допустимыми для импорта. Отсутствующий маркер, неизвестная экспозиция и неполная запись не являются повреждением структуры. Ошибка называет файл и индекс кадра; отклонённый импорт не блокирует последующие запуски.

Сохранение проверки и отображение результата имеют отдельные статусы. При отказе хранилища запись остаётся в памяти и доступна через «Экспорт проверки» до закрытия страницы. Ошибка анализа или рендера не отменяет успешное сохранение. Завершение освобождает состояние управления через `finally`; при ошибке сцена очищается и кнопки восстанавливаются.

Для выбранной проверки отдельно показываются:

- Сохранность записи, число пропущенных event_id, dropped_count и наличие footer в NDJSON. Отсутствующие счётчики legacy JSON отмечаются как недостаточные данные, без выдуманного нуля. Незавершённость опыта телефона и сохранность файла — разные признаки.
- Кадры, прочитанные коды и **доля прочитанных кодов по всему файлу**. В знаменателе все кадры файла, включая возможное время до и после показа.
- Обнаруженные run_id, совпадения с показанными step_id выбранной проверки, отсутствующие шаги и посторонние коды. Прерванная проверка явно помечается; ожидаемыми показанными шагами считаются только фактически записанные в `steps[]`.
- Настоящий декодируемый JPEG из импорта, отдельно результат поиска четырёх угловых меток. Метаданные размеров без JPEG не заменяют изображение. Отсутствие JPEG не блокирует анализ чтения; Android сохраняет его только после первого успешного чтения sync-кода.

Для фаз используются только пригодные `capture_ns`, без подстановки analyzer-времени. Каждый прочитанный ожидаемый код ограничивает одно общее смещение камера–браузер интервалом его фактического показа, включая сохранённый конец последнего шага. Перестановка шагов, некорректные времена/номера кадров либо пустое пересечение делают сопоставление несовместимым. Без конечных границ смещения данных недостаточно. Для неизменного кода и переключений учитываются только кадры, которые при всех допустимых смещениях лежат внутри соответствующей фазы. Остальные кадры не входят в фазовые счётчики; при пустом наборе выводится «недостаточно данных». Это не полная доля чтения за фазу и не доказательство поведения в пропусках событий.

«Проверено камерой» означает наличие импортированных кодов с ожидаемыми run_id/step_id; UI показывает, сколько разных показанных шагов прочитано. Это не доказывает непрерывное чтение, пригодность всех переключений или пространственную калибровку. Нулевое чтение даёт результат «Код не прочитан ни в одном кадре. Причина по журналу не установлена». Программное чтение canvas production-декодером проверяет формат, физическая проверка на телефоне выполняется отдельно по [инструкции](README.md#проверка-чтения-sync-кода).
