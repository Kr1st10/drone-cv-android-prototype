# Участие в разработке

Правила для участников университетского Android/CV-проекта. Постоянные инструкции находятся в [AGENTS.md](AGENTS.md), проверенное состояние — в [PROJECT_STATE.md](PROJECT_STATE.md), техническая навигация — в [docs/index.md](docs/index.md).

## Начать изменение

Прочитайте PROJECT_STATE, сверьте нужный участок с кодом и `git log`. Исторический отчёт не доказывает состояние текущего commit. Настройте окружение по [быстрому старту](docs/getting-started.md); перед работой проверьте `git status` и сохраните посторонние локальные изменения.

Работайте в отдельной ветке (`codex/описание-задачи` для агента). Публикуйте небольшие логические коммиты и PR в `main` согласно AGENTS. Не переписывайте работающую архитектуру за пределами этапа; новые версии зависимостей задавайте в Version Catalog. Изменение контракта сопровождайте обновлением потребителей и проверок. Порядок замены модели/отчёта — [типовые задачи](docs/guides/common-tasks.md).

## Проверить и оформить PR

В PR укажите конкретный триггер/проблему, получившееся поведение, область правок, выполненные команды и ограничения. Разделяйте локальную сборку, GitHub Actions, выполнение device tests и испытания телефона. Не выдавайте compilation, skipped или просмотр протокола за успешный запуск. Список команд/отчётов — [testing](docs/development/testing.md).

Не добавляйте фиктивные детекции, показатели FPS и качества. Веса, датасеты, local.properties, keystore, токены и журналы с личными данными не коммитятся. Сообщения об уязвимостях рассматриваются по [SECURITY](SECURITY.md).

## Обновить каноническую документацию

| Изменение | Обновляемое место |
|---|---|
| Версии, default, env/CLI-параметр | [configuration](docs/reference/configuration.md), краткий старт, если изменился запуск |
| Контракт/тип/исключение | KDoc/docstring и [api](docs/reference/api.md); сериализуемые данные также [data-model](docs/reference/data-model.md) |
| Конкурентность/ресурсы/геометрия | [lifecycle](docs/internals/detection-lifecycle.md), [data-flow](docs/architecture/data-flow.md), соответствующие тесты |
| Компоненты/границы | [overview](docs/architecture/overview.md), при известном контексте — ADR без вымышленных обоснований |
| Установка/выпуск/восстановление | [deployment](docs/deployment.md), [runbook](docs/operations/runbook.md), сведения о реальном выпуске, если он появился |
| Способ проверки/CI | [testing](docs/development/testing.md), соответствующий протокол |
| Модель/данные/исследование | [MODEL](ml/MODEL.md), manifest, соответствующий отчёт; RESEARCH только при новых проверенных знаниях |
| Завершённая задача | Краткое обновление PROJECT_STATE: сделано, проверено, ограничения |

Документация меняется в том же PR, что поведение. У каждого факта должно быть одно подробное описание; в других местах используйте относительную ссылку. Новые Markdown-файлы называйте `lowercase-kebab-case.md` (стандартные корневые README/CONTRIBUTING/SECURITY сохраняют свои имена), UTF-8/LF, один H1, языки fenced code, проверенные ссылки/диаграммы. Достоверность важнее объёма.

## Review и ограничения процесса

Рецензент сверяет существенные утверждения с исходниками, результаты с отчётами, инструкции — с заявленной средой. Непроверенные команды и недоступные устройства должны быть отмечены. После исправлений повторяются затронутые проверки; лишний полный экспорт/обучение не нужен. Изменения CI и политики выпуска не следует скрывать внутри документационного PR.

В репозитории не установлены именованные владельцы страниц, SLA review и подтверждённые required checks защиты main. Эта инструкция задаёт проверяемый порядок подготовки PR, но не приписывает GitHub-настройкам отсутствующие сведения. Приёмка по внутреннему стандарту и открытые пробелы — [аудит](docs/documentation-audit.md).
